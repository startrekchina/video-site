## 1. 问题陈述

一个小圈子的《星际迷航》粉丝希望在同一个地方观看全部剧集和电影，按自己的节奏记录看到了哪里，并整理和分享片单。现有的观看渠道很分散，中文字幕和中文剧集资料不全，也没有只属于这个圈子的空间。

站长只能用业余时间维护，希望运维工作尽量少、每月花费可控，整套系统放在 Cloudflare 上。

## 2. 解决方案

建一个邀请制的私人观看站，片库、播放和成员功能只对受邀成员开放：

- 访客可以查看不展示片库的首页和关于页，以及登录、邀请码注册和账号恢复入口。
- 成员必须持邀请码注册，注册时提供邮箱并通过邮件验证，之后用用户名和密码登录，可以加上通行密钥和 TOTP 二步验证。
- 登录后可以浏览全部作品，按网格或首映年份时间轴查看剧集和电影，在线播放 MP4 视频，并切换中文或英文字幕。
- 站点自动记录观看进度，首页显示“继续观看”。成员可以收藏作品，也可以建立、排序和分享站内片单。
- 成员可以在单集或电影的播放页发表评论、回复和赞踩，讨论只对成员开放。
- 成员可以用邮箱找回密码，也可以修改注册邮箱并完成新邮箱验证，同时会收到封禁等重要安全事件的通知邮件。
- 管理员负责发放邀请码、封禁成员、重置账号，以及删除违规的评论和回复。
- 站长在本地用离线命令行工具把视频、字幕和剧集资料导入系统。网站本身不提供内容上传或编辑功能。

### 2.1 法律风险声明

《星际迷航》系列的版权归 Paramount 所有。本站的片源是站长自己持有的拷贝，但提供给其他人观看，在法律上仍然属于未授权分发。“非营利”和“粉丝向”都不构成免责理由。

Cloudflare 的可接受使用政策（AUP）禁止托管侵权内容。一旦收到 DMCA 投诉，可能导致内容下架、账号被封，以及 R2 中的数据丢失。站长已知晓并自行承担这一风险。

本项目不设计任何规避 DMCA 或检测的机制。访问控制只用于限定谁是成员。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| 作品 | 一部电影或一部剧集（系列），和 manifest 中的一条主海报一一对应 |
| 季 | 剧集下的一季，有自己的季海报 |
| 集 | 某一季下的一集 |
| 可播放单元 | 可以直接播放的东西：一集，或一部电影 |
| 媒体文件 | 存在 R2 中、属于某个可播放单元的视频文件（v1 只有 MP4） |
| 字幕轨 | 挂在可播放单元上的一条外挂字幕（v1 为 VTT，分中文和英文） |
| 成员 | 已注册并通过邮箱验证的普通用户 |
| 管理员 | 能管理成员和邀请码的用户 |
| 邀请码 | 一次性的注册凭证，记录是谁发出的 |
| 邀请链 | 成员之间“谁邀请了谁”的关系，出问题时用来追溯和连带处理 |
| 邮箱验证 token | 注册或改邮箱后发到目标邮箱的一次性凭证，绑定成员、目标邮箱和用途，用于确认邮箱归属 |
| 改邮箱待验证 | 已验证成员已提交新邮箱、但新邮箱尚未验证通过的状态；此时旧邮箱及旧邮箱找回仍然可用 |
| 待验证账号 | 已提交注册、但尚未通过邮箱验证的账号，不能登录成员功能 |
| 通知邮件 | 系统主动发出的邮件：管理员重置链接、封禁等安全提醒 |
| 播放 token | Worker 签发的短期凭证，只对一个媒体文件有效，并绑定到具体成员 |
| 恢复码 | 成员自己保存的一次性码，用于找回账号 |
| 重置链接 | 成员用邮箱找回或管理员签发的一次性账号重置入口；同一账号任一时刻最多一个有效链接 |
| 片单 | 成员自己整理的有序作品或剧集清单 |
| 评论 | 成员在一个可播放单元下发表的讨论内容 |
| 对话 | 一条评论及其按时间排列的回复 |
| 赞踩 | 成员对评论或回复的赞同或反对反馈，与作品评分无关 |

## 4. 范围与规模

### 4.1 片库

片库以 `public/assets/posters/star-trek/manifest.json` 为准。v1 不开发“收录新内容”的功能，但数据模型要按通用的作品、季、集结构来设计，以后扩展时不需要改表结构。

- 电影 14 部：1979 年到 2025 年，包括《Section 31》。
- 剧集 13 部，共 52 季，约 950 集（集数为估算）：TOS、TAS、TNG、DS9、VOY、ENT、DIS、Short Treks、LD、PIC、PRO、SNW、Starfleet Academy。

当前原型中已实现的产品页面和交互全部属于 v1。下表用于检查覆盖情况；功能规则以本文的用户故事和实现决策为准。

| 页面或能力 | v1 范围 |
| --- | --- |
| 访客首页 `/`、关于 `/about` | 桌面星图、手机登舰指南、邀请码入口、通行密钥和密码登录入口、站点说明与守则 |
| `/login`、`/register`、`/recover`、`/reset/:token` | 密码、通行密钥、TOTP、邀请码状态、邮箱填写与发信、恢复码展示与保存、恢复码找回、一次性重置链接 |
| 邮箱验证 `GET /verify-email`、待验证提示页 | **原型没有**：验证邮件链接落地页、验证结果反馈、重新发送验证邮件入口 |
| 邮箱找回密码 `GET /forgot-password` | **原型没有**：提交邮箱、统一成功提示、邮件中的重置落地页 |
| 成员修改邮箱 `/account` | **原型没有**：提交新邮箱的两种身份验证路径、验证邮件落地页、验证完成后的替换与旧邮箱失效 |
| 成员首页 `/` | 影院式推荐或续播舞台、继续观看刻度尺、收藏、剧集和电影分区 |
| `/series`、`/movies`、全站搜索 | 剧集和电影浏览、网格与首映年份时间轴、中文或英文作品名搜索 |
| `/title/:slug` | 作品资料、收藏和加入片单、季切换、带单集剧照和观看状态的选集列表 |
| `/watch/:unitId` | 播放、拖动、字幕、键盘控制、续播和观看状态、下一集提示、加入片单、评论与回复 |
| `/library`、`/playlists`、`/playlists/:id` | 收藏、片单创建和删除、条目增删排序、私有或站内公开、按顺序播放入口 |
| `/invites`、`/account`、`/admin` | 邀请、账号安全和会话、成员及邀请链管理、封禁、重置链接、额度与管理员身份 |
| 跨页面交互 | 跟随系统或浅色/深色主题、响应式布局、手机搜索与菜单、回到顶部、快捷键、复制和操作反馈、404 页面 |

原型中的 PROTO 控制台、身份切换、虚构用户、模拟接口、固定密码和验证码、人为等待时间、自生成测试片段，以及已删除的设计比较方案，不属于正式产品功能。原型已有的加载、空数据、失败和成功反馈需要接入真实数据；已知缺陷不能作为正式版的预期行为。此前已确认但尚未在原型中实现的后端、导入和运维需求仍然保留。

## 5. 用户故事

### 5.1 访客与注册

1. 作为访客，我希望能查看不展示片库的首页、关于页，以及登录、注册和账号恢复页，了解如何加入；作品资料、搜索、媒体、观看记录、片单和讨论只对成员开放。
2. 作为访客，我希望用邀请码注册账号，这样只有受邀的人才能加入。
3. 作为访客，我希望邀请码无效、过期或已被使用时能看到明确的提示，这样我知道该去找邀请人重新要一个。
4. 作为访客，我希望注册时自己设置用户名、密码和邮箱，注册后收到验证邮件，验证通过才能使用成员功能，这样账号一定对应一个真实可联系的人。
5. 作为新成员，我希望注册完成后立刻拿到一组恢复码并被提醒妥善保存，这样以后忘记密码也能自己找回账号。
6. 作为搜索引擎的爬虫，我不应该收录本站的任何页面。

### 5.2 登录与账号安全

7. 作为成员，我希望用用户名和密码登录。
8. 作为成员，我希望绑定通行密钥，这样可以不输密码直接登录。
9. 作为成员，我希望开启 TOTP 二步验证，这样即使密码泄露，账号也不会被盗。
10. 作为成员，我希望连续输错密码时系统会限流或弹出人机验证，这样我的账号不容易被暴力破解。
11. 作为成员，我希望能查看自己有哪些登录会话，并退出不认识的会话。
12. 作为成员，我希望能修改密码、重新生成恢复码、解绑通行密钥或二步验证设备。
13. 作为成员，我希望忘记密码时可以用恢复码重设，不需要找管理员。
14. 作为成员，我希望恢复码也丢了的时候，管理员能给我一个一次性的重置链接。

### 5.3 浏览片库

15. 作为成员，我希望在首页看到“继续观看”，以及按剧集和电影分类的全部作品。
16. 作为成员，我希望在作品页看到中文标题、简介、年份和海报；中文资料缺失时显示英文。
17. 作为成员，我希望在剧集页按季浏览，每一集都显示标题、简介、时长、我的观看状态和一张小尺寸单集剧照；剧照仅用于非播放页的选集列表，缺失时显示同尺寸占位，不用作品或季海报替代。
18. 作为成员，我希望按作品名（中文或英文）搜索作品。
19. 作为成员，我希望在一部作品的季和集之间顺畅地切换。

### 5.4 播放

20. 作为成员，我希望点击一集或一部电影就能在网页里直接开始播放。
21. 作为成员，我希望可以随意拖动进度条，播放能马上从新位置开始。
22. 作为成员，我希望在中文字幕、英文字幕和关闭字幕之间切换。
23. 作为成员，我希望看完两小时的电影都不会因为凭证过期而中断。
24. 作为成员，我希望用键盘控制播放器（播放、暂停、快进、快退、调节音量、全屏）。
25. 作为成员，我希望一集播完后看到下一集提示，可以立即播放、取消倒计时，或等倒计时结束后继续播放；浏览器不允许自动播放时，应给我明确的手动播放入口。
26. 作为站长，我希望复制出去的视频地址很快就失效，而且只对原来的成员和这一个文件有效，这样链接被转发出去影响也有限。

### 5.5 观看进度与片单

27. 作为成员，我希望系统自动记住每一集和每部电影看到了哪里，下次打开时从那里继续。
28. 作为成员，我希望看到接近结尾时自动标记为“已看完”，也可以手动标记为已看或未看。
29. 作为成员，我希望在剧集页一眼看出哪几集已经看过。
30. 作为成员，我希望在不同设备上看到同样的观看进度。
31. 作为成员，我希望收藏作品。
32. 作为成员，我希望建立有序的片单（比如“TNG 必看 20 集”），片单里可以放作品，也可以放单集。
33. 作为成员，我希望把片单设为站内公开，让其他成员也能看到。

### 5.6 邀请

34. 作为成员，我希望看到自己还剩多少个邀请码，并能生成邀请码发给朋友。
35. 作为成员，我希望看到自己发出的邀请码是否已被使用，以及是谁用的。
36. 作为成员，我希望能作废还没被使用的邀请码。

### 5.7 管理员

37. 作为管理员，我希望生成邀请码不受数量限制。
38. 作为管理员，我希望调整每位成员的邀请额度。
39. 作为管理员，我希望查看成员列表，以及每个人的邀请人和被邀请人。
40. 作为管理员，我希望封禁一名成员，并可以选择连带封禁他邀请的人。
41. 作为管理员，我希望被封禁的成员立即无法登录，已经在播放的视频最多 30 分钟后停止。
42. 作为管理员，我希望为成员生成一次性重置链接，通过站外渠道发给对方。
43. 作为管理员，我希望把其他成员设为管理员，或取消管理员身份。

### 5.8 站长与运维

44. 作为站长，我希望在本地用一个命令行工具把视频、字幕和剧集资料导入 staging 或 prod 环境。
45. 作为站长，我希望导入工具能重复运行而不出问题：再跑一次只会补上缺少的部分，不会产生重复数据。
46. 作为站长，我希望导入工具在上传前检查视频格式，格式不对时明确提示我去重新转码。
47. 作为站长，我希望剧集标题和简介由导入工具从 TMDB 自动拉取中文和英文版本，不用我手动整理。
48. 作为站长，我希望 staging 和 prod 完全隔离，这样在 staging 上试错不会影响成员。
49. 作为站长，我希望数据库每天自动备份到 R2，同时推送一份加密副本到 Cloudflare 之外的 WebDAV 地址。
50. 作为站长，我希望每月的开销都在预算以内，不用盯着账单。

### 5.9 原型新增与细化的用户故事

以下编号接续原有 1–50，保留已有编号便于追踪。

51. 作为访客，我希望桌面首页展示星图、手机首页展示登舰指南，并能从首页使用通行密钥登录、进入密码登录或填写邀请码注册。
52. 作为访客或成员，我希望在关于页了解本站、加入方式、成员守则、隐私与数据、账号找回、版权说明和技术说明。
53. 作为成员，我希望首页用影院式舞台展示当前续播作品，并通过带进度的刻度尺切换或播放其他继续观看条目；没有记录时能看到推荐起点。
54. 作为成员，我希望在剧集和电影浏览页切换海报网格与首映年份时间轴，并从两种视图进入作品页。
55. 作为成员，我希望在单集或电影的播放页发表评论，用受限的 Markdown、表情和预览表达内容。
56. 作为成员，我希望展开评论的对话、回复评论或其中某位成员，并在切换对话时保留各自未发送的草稿。
57. 作为成员，我希望对评论和回复赞同或反对，再次点击可以取消；赞显示数量，踩仅参与排序、不显示数量。
58. 作为成员，我希望按智能、最新或最早排序查看评论，分页浏览评论和分批展开回复；点赞时列表不应突然重新排列。
59. 作为成员，我希望评论发送时有明确反馈且不能重复提交，发送成功后容易找到新内容，过长正文可以展开或收起。
60. 作为成员或访客，我希望页面适配桌面与手机，并可以选择跟随系统、浅色或深色主题；手机上能方便地打开搜索、菜单和回到顶部。
61. 作为成员，我希望通过键盘快捷键打开搜索、切换主题、控制播放，以及发送评论；输入文字时普通字母快捷键不应干扰输入。
62. 作为成员或管理员，我希望复制邀请码、邀请链接、重置链接和恢复码时得到明确反馈，异步操作也有加载、成功或失败状态。
63. 作为成员，我希望创建和删除自己的片单、添加或移除条目，在桌面通过按钮排序、手机通过滑动排序，并通过“按顺序播放”入口观看片单内容。

### 5.10 邮箱与通知

以下编号接续 1–63。

64. 作为访客，我希望注册时填写邮箱，注册后收到一封验证邮件，点击其中的链接完成验证，这样我的账号绑定了一个真实邮箱。
65. 作为待验证账号，我希望在验证前看到明确说明，被告知成员功能要验证后才能使用，并且能重新发送验证邮件。
66. 作为待验证账号，我希望重新发送验证邮件时受到限流和频率限制，这样别人不能拿我的邮箱反复触发发信。
67. 作为成员，我希望验证邮件里的链接有有效期，过期后可以重新申请，避免一个旧链接长期有效。
68. 作为成员，我希望用邮箱收取密码重置邮件，这样忘记密码时不必先找恢复码。
69. 作为成员，我希望验证邮件和找回邮件只说明必要的操作，不包含我的密码、恢复码或完整的账号资料。
70. 作为成员，我希望在账号被连带封禁等重要安全事件发生时收到一封通知邮件。
71. 作为管理员，我希望为成员生成重置链接后，系统能代我把这封通知邮件发出去，这样我不用手动转到站外渠道。

## 6. 实现决策

本节保留已确认的产品行为，补充后端实现约束和接口草案。表名、字段名、接口路径用于指导迁移和 loader / action 开发，不要求照搬认证库的内部命名。第 6.13、6.16 节原列出的策略已确认；对应模块的实现与验证门槛见 6.16，已确认规则索引见 6.13。

### 6.0 邮箱验证与发信

邮箱验证是 v1 的注册门槛，不是可选的加固项。它同时承担注册验证与改邮箱验证、密码找回、通知类邮件和安全提醒四类用途。成员在账号页自助修改注册邮箱也属于 v1，规则见 6.0.4。

#### 6.0.1 注册与验证流程

- 注册表单在用户名、密码和邀请码之外**必须**收集邮箱。邮箱格式和长度在服务端校验，不接受只有客户端校验。
- 注册提交成功后创建**待验证账号**，不建立正式成员会话，也不授予任何成员功能。此时邀请码已在同一原子提交中消费（沿用 6.2.2 的边界），不能因为邮箱未验证而回退邀请码。
- 系统立即发送一封验证邮件，包含一次性验证链接。邮件正文只说明如何完成验证，不含密码、恢复码或完整账号资料。
- 成员点击链接后，服务端校验 token 的哈希、有效期和消费状态，原子标记邮箱已验证；验证成功后**不自动建立成员会话**，返回正常登录，让成员自行登录。
- 验证 token 绑定**成员 + 目标邮箱 + 用途**，只用于该用途和该目标邮箱，不能拿注册验证 token 去验证改邮箱申请，反之亦然。用途以 `purpose` 和目标 `target email` 等最低所需字段区分。
- 验证链接的默认有效期为 **24 小时**，与其他一次性凭证一样只存哈希、不写日志、不进 `Referer`。
- 待验证账号可以重新发送验证邮件，但受 6.0.3 的限流约束。已确认的硬规则是：token 不可跨用途消费（注册验证 token 换不了改邮箱，反之亦然），**同一用途**的新申请原子失效该成员该用途下未消费的旧 token 并替代未完成的申请，同一目标成员任一时刻最多一个有效验证链接。跨用途之间是否互相撤销按“同一成员最多一个有效 token”的最低方案实现，这是防重放的实现边界，不得因此改变已确认的改邮箱行为（新申请替代未完成的申请、验证前旧邮箱与旧邮箱找回仍可用）。
- 待验证账号在验证前**不能**登录成员功能、不能读取片库、不能发表讨论。越权访问按 6.5 的未认证处理，返回登录跳转而不是泄露账号是否存在。
- 邮箱唯一性：同一邮箱不能同时绑定到两个账号，也不能与任何账号的待验证新邮箱冲突。冲突时的提示语义与用户名冲突一致，不泄露该邮箱是否已被注册。
- **待验证账号不自动清理**：不设定期回收期限，也不因为长期未验证而释放已占用的用户名或邮箱，邮箱仍受 6.0.3 的 60 秒 / 滚动 60 分钟 5 次的验证用途配额约束，只能按配额重发。注册时已消费的邀请码不因账号未验证而返还。

#### 6.0.2 邮箱作为找回通道

- 成员可以用邮箱申请密码重置：提交邮箱后，系统向该邮箱发送一次性重置链接。**无论邮箱是否存在，都返回相同的成功响应**，不区分“邮箱未注册”，避免枚举成员。
- 邮箱重置链接与 6.4 的恢复码、管理员重置链接是**并列的第三条找回路径**，不替代前两者。三条路径都要能独立走通。
- 邮箱重置成功后只更新密码，**保留已开启的 TOTP 验证器和已绑定的通行密钥**，并撤销该成员的全部旧会话；不自动建立会话，返回正常登录。因此遗失验证器时邮箱路径无法解决，仍需恢复码或管理员重置链接。
- 每次签发邮箱重置链接都会撤销该账号**所有来源**的旧重置链接（含此前未用的邮箱重置链接和管理员签发的链接），任一时刻最多一个有效重置链接；重置成功后同样撤销当前所有旧重置链接，避免已寄出的旧链接被重放。链接有效期沿用默认 24 小时。**发送失败不恢复已撤销的旧链接**，不因为邮件没发出去就把旧入口放回来。
- 被封禁成员不能通过邮箱重置解除封禁。

#### 6.0.3 发信通道与限流

- 发信使用**站长已经购买的发件服务**，通过其 **HTTPS API** 用 `fetch` 调用；服务商与 HTTP API 通道已确认，不再比较或选择其他服务商，不使用 SMTP。
- 邮件服务商的 API key 放在 Worker Secrets 中，不写进仓库、不暴露给浏览器、不进日志。
- 每次业务操作只发起一次发信 API 请求；失败或超时不自动重试。超时记录为发送结果未确认，不能宣称邮件确定未送达。成员可重新发送验证邮件或重新申请邮箱找回，仍受限流与一次性凭证规则约束；管理通知发送失败由站长处理，不增加自动重试任务。
- 发信失败不能阻塞注册主流程：注册成功后即便发信失败，账号和邀请码消费状态仍然有效，并返回“已发送，若未收到可重新发送”的提示；服务端记录脱敏失败原因供排查。
- 成员的验证邮件、改邮箱验证邮件与邮箱找回按**目标邮箱摘要＋用途**限流：至少间隔 **60 秒**，滚动 **60 分钟最多 5 次**。首次发送、失败及超时的发送尝试均计入；注册验证、重发验证与改邮箱验证共用验证用途配额，邮箱找回单独计数。改邮箱验证按新邮箱摘要计数。不存在账号的邮箱找回请求走相同计数和响应规则，不因更换 IP 绕过。来源标识仅作辅助防滥用信号。
- 管理员代发重置邮件和封禁安全提醒不设站内发信频率上限；已购服务自身的套餐和 API 限制仍须遵守。发送失败或服务限流不回滚已经成功的管理操作，不自动排队补发。
- v1 保留脱敏发送结果和错误原因，由站长查看日志与已购服务后台人工排查；不增加主动失败告警或投递/退信 webhook。API 接受请求只表示服务已接受，不宣称收件人已收到邮件。
- 邮件内容不含一次性凭证原值以外的敏感数据；链接 token 只在邮件正文中出现，服务器日志只记录邮箱的不可逆摘要与发送结果。

- 发件身份沿用已购服务的现有 From；已有 Reply-To 则沿用，没有则不额外添加。域名及 SPF/DKIM/DMARC 由站长在现有服务中维护，不重新选域名或服务商。接入前由站长提供现有 API 文档与本机/平台配置，不将凭证写入公开仓库。

成员发信的计数按目标邮箱和用途由 D1 条件写入维护，不能仅用按 Cloudflare 位置生效的近似计数实现这一上限。不可逆的邮箱摘要用于计数，不保留无账号邮箱的原文；滚动窗口外的计数可清理。成员发信间隔 `60 秒`、每用途滚动 `60 分钟` 最多 `5 次` 与 6.3.2 的全部限流数值一并纳入集中配置。

接入时以已购服务的 API 文档为依据，核对鉴权方式、请求与响应格式、错误码及实际套餐限额；API 地址和凭证仅通过本机/平台配置提供，不写入公开文档。发信投递策略及发件身份已确认；现有 API 文档与真实配置属于接入前置材料，不作为重新选型事项。

#### 6.0.4 修改注册邮箱

- 产品规则：**当前邮箱未完成验证时可直接更改；已验证的邮箱，要等新邮箱验证通过后才替换旧邮箱。** 改邮箱是 v1 的成员自助能力，不新增管理员代改入口。
- 身份验证按账号状态分两条路径，证明归属的凭证都必须在服务端校验：
  - **未验证账号**：提交 `username` 和 `currentPassword`，并带匿名表单的 CSRF 挑战。校验通过后**直接把邮箱替换为未验证的新邮箱**（`email_verified_at` 仍为空），撤销旧验证 token，按 6.0.3 向新邮箱重新发送验证邮件。
  - **已验证账号**：需要当前成员会话加当前凭证再验证；已开启 TOTP 的成员必须完成 TOTP。校验通过后进入“改邮箱待验证”状态：新邮箱单独保存，旧邮箱及旧邮箱找回在此期间**保持可用**，成员照常登录、收藏、看片和讨论。
- 改邮箱验证邮件使用 6.0.1 的验证 token 规则：绑定成员、新邮箱和改邮箱用途，默认 24 小时有效，只存哈希，新申请原子撤销该成员改邮箱用途下未消费的旧 token，替代此前未完成的申请。不能用注册验证的 token 消费改邮箱验证，反之亦然。
- 邮箱唯一性由服务端控制：新邮箱不能与任何账号的当前邮箱或待验证新邮箱冲突，冲突提示与用户名、注册邮箱冲突保持同一语义，不泄露该邮箱是否已被使用。
- 新邮箱验证通过后在一次原子提交内替换 `email` / `email_key`、写入 `email_verified_at` 并清除待验证新邮箱；同时撤销该账号**所有来源**的旧重置链接，防止旧邮箱已经寄出的重置链接把账号夺回。
- 失败与异常的处理：验证失败、超时、放弃或发信失败，都**不改变已验证的旧邮箱**，成员仍能用旧邮箱登录和找回密码。发送新验证邮件失败时，已经在业务上成功的变更（未验证账号的直接替换）保留，已验证账号的待变更状态也保留，成员可在配额允许范围内重新发送。
- 改邮箱**不撤销现有会话**，也不把改邮箱表述为“已登出”；换邮箱不改变成员的角色、观看进度、片单和讨论归属。本文不新增改邮箱完成后的通知邮件。
- 未验证账号这条匿名密码校验路径按 6.3.2 的账号/凭证摘要与 operation 计数限流，与其他认证入口同一组数值。

### 6.1 总体架构

- 全站使用 React Router v7 框架模式，前后端作为一个 Worker 部署在 Cloudflare Workers 上。页面的登录校验在服务端的 loader 中完成。
- D1 存放所有结构化数据，包括成员、会话、邀请码、剧集资料、观看进度、片单、评论、回复和赞踩记录。
- R2 存放媒体文件和字幕文件。R2 存储桶不公开，只通过 Worker 访问。
- 海报和非播放页选集列表使用的小尺寸单集剧照留在仓库的 `public/` 目录下，作为 Workers 静态资源公开访问，不需要登录。站长知道这样会让外人看出这是一个星际迷航站，并接受这一点。
- 单集剧照以 `public/assets/stills/star-trek/manifest.json` 为准，按作品 TMDB ID、季号、集号匹配，可为空。默认输出 240×135 的 WebP（质量 55），保留原始画面比例并补边；列表按小尺寸 16:9 展示，懒加载，加载失败时保留同尺寸占位。播放页的选集列表不显示剧照，视频时间轴的预览缩略图仍在范围外。
- 界面以简体中文为主，不做 i18n；保留原型中的英文作品回退资料、字幕语言名称、星图标注、等宽辅助标签和评论时间格式。
- 全站返回 `X-Robots-Tag: noindex`，并配置 `robots.txt` 禁止所有爬虫。公开访客页同样不允许索引。
- 原型既是页面和交互基准，也是前端代码的迁移来源。正式应用使用 React Router 框架模式和真实的服务端权限校验，优先沿用经审查的页面、展示组件、样式和已定稿交互，不要求全面重写前端；原型保留、迁移边界和验收遵循 6.15。

#### 6.1.1 服务端边界与公共约定

- 路由模块负责 loader / action 的输入输出，认证、D1 查询、签名、R2 和备份逻辑放在 `*.server.ts` 或 Worker 服务端模块。浏览器构建不能引用 Secrets、数据库绑定或对象存储键。
- 每个受保护的 loader、action 和资源路由都单独校验会话、成员状态和权限，不能只依赖父布局 loader；框架的数据请求、预取和直接 HTTP 请求也受同一规则约束。`userId` 和角色取自服务端会话，不接受客户端指定当前身份。
- 会话 Cookie 建议命名为 `__Host-session`：随机不透明值，`HttpOnly; Secure; SameSite=Lax; Path=/`，不设置 `Domain`；D1 保存其哈希而非原值。登录完成时换发会话标识；注册、邮箱验证和三种恢复成功后都不建立会话（6.0.1、6.4），以后若增加自动登录路径也必须使用全新标识；退出时同时撤销 D1 记录并清除 Cookie。期限、活跃与续期规则见 6.3.3。
- 改变状态的请求走 action 或非 GET 接口，校验 `Origin` 与配置的 `APP_ORIGIN` 一致，并验证绑定当前会话或匿名表单挑战的 CSRF token；登录、注册和恢复也受保护。拒绝跨站请求，不开放带凭证的跨域媒体访问，`SameSite` 不能代替 CSRF 校验。跳转目标只接受站内相对路径。
- JSON action 成功结构为 `{ data, requestId }`，失败为 `{ error: { code, message, fieldErrors?, challenge? }, requestId }`；`challenge` 仅给出所需的 `turnstile` 或 `totp` 挑战及不透明挑战 ID。页面 loader 返回页面所需的类型化数据；表单提交可在成功后返回 `303` 站内跳转，媒体返回字节流，不套 JSON。
- `400` 表示格式或字段不合法；`401` 表示未认证或凭证无效；`403` 表示已认证但权限不足、CSRF 或挑战未满足；`404` 表示资源不存在或不可见；`409` 表示已消费、版本冲突或额度不足；`429` 表示限流；依赖暂不可用返回 `503`，意外错误返回脱敏 `500`。限流提供可重试信息，不能泄露内部 SQL、栈、R2 key 或上游原始错误。
- 稳定错误码至少区分 `AUTH_REQUIRED`、`AUTH_INVALID`、`CSRF_INVALID`、`TURNSTILE_REQUIRED`、`TOTP_REQUIRED`、`INVITATION_INVALID`、`INVITATION_EXPIRED`、`INVITATION_USED`、`INVITATION_REVOKED`、`QUOTA_EXHAUSTED` 和 `REVISION_CONFLICT`；前端按 code 处理，不解析中文 message。邀请码无效使用 `400`，其已用/过期/作废及额度不足使用 `409`。
- 受保护 HTML 页面未登录时跳转登录页；6.5 列明的公开访客页无需登录。受保护 JSON 和媒体接口返回错误而非登录页 HTML。登录、恢复不区分“用户名不存在”和“密码/恢复凭证错误”；注册仍按原文区分邀请码无效、过期、已用和作废，不返回邀请人的私人资料。
- 登录态 HTML、loader 数据、认证 action、邀请凭证和媒体响应使用 `Cache-Control: private, no-store`，禁止共享缓存绕过鉴权。公开静态资源可以按文件版本缓存；静态资源、重定向、错误和媒体响应同样带 `X-Robots-Tag: noindex`。Workers 静态资源头与 Worker 生成响应头分别配置，不能假定其中一处覆盖另一处。
- 动态响应设置 `Referrer-Policy: no-referrer` 和 `X-Content-Type-Options: nosniff`。浏览器响应不含内部 R2 key/URL 或 Worker Secrets；只有对应签发/绑定流程向有权接收者返回必要的一次性凭证、TOTP 绑定材料或短期授权地址，列表、无关响应和错误不得包含凭证原值或完整 token。日志只记录请求 ID、路由模板、状态、错误码和必要的不透明资源 ID，始终不记录 Cookie、密码、邀请码、恢复码、TOTP、其他凭证原值、完整 token 或完整 URL；平台自动 URL 日志也必须验证脱敏，不能只清理应用日志。

### 6.2 数据模型（概念层）

- 作品分为电影和剧集两种。剧集下有季，季下有集。电影和集统一抽象为“可播放单元”，播放、进度、收藏和片单都只和可播放单元或作品打交道，不用区分电影和剧集。
- 作品、季、集都记录 TMDB ID，中英文标题和简介分开存储。展示时优先用中文，中文缺失就回退到英文。
- 一个可播放单元对应一个或多个媒体文件，媒体文件记录格式、码率等属性。v1 每个单元只有一个 MP4，以后加 HLS 或多档码率时只需要增加记录。
- 一个可播放单元可以挂多条字幕轨，每条记录语言、格式和显示名称。v1 只用 VTT，以后接入 ASS 时不需要改表结构。
- 片单里的条目既可以是作品，也可以是可播放单元，并且保留排序。
- 邀请码记录发出人、使用人、状态和有效期。成员表记录邀请人，邀请链由这两者串联出来。
- 评论绑定到可播放单元和作者；回复绑定到所属评论和作者，并可记录被回复的成员。电影和单集使用相同的讨论结构。
- 赞踩记录绑定成员和评论或回复，同一成员对同一对象最多有一个当前反馈；可切换赞或踩，也可取消。

#### 6.2.1 字段与关系草案

下表是既有对象的存储映射，不增加新的业务对象。所有 ID 是稳定的内部 ID，和 TMDB ID 分开；时间统一使用 UTC，HTTP 输出 ISO 8601 时间，位置和时长以秒为单位。中文和英文原始资料保留，空中文按缺失处理。

| 作品 `works` | `id, kind, tmdb_id, title_zh, title_en, overview_zh, overview_en, year, poster_asset`；`kind` 仅为 `movie` / `series`；唯一键 `(kind, tmdb_id)`，不能把电影和剧集的 TMDB 数字空间混为一谈。 |

| 邮箱验证凭证 `email_verification_tokens` | `id, user_id, purpose, target_email_key, token_hash, created_at, expires_at, consumed_at`；`purpose` 区分注册验证与改邮箱验证，`target_email_key` 绑定本次要验证的目标邮箱（改邮箱时为新邮箱）。`token_hash` 唯一，外键指向成员。只存哈希，不存原值；同一用途签发新 token 时原子撤销该成员该用途下未消费的旧记录，跨用途不可消费；同一成员任一时刻最多一个有效 token 是防重放的最低实现约束。有效期默认 24 小时。 |
| 邮件发送记录 `email_deliveries` | `id, user_id?, to_email_key, purpose, provider_message_id?, status, error_code?, created_at`；`purpose` 区分注册验证、重发验证、密码找回、管理员通知、安全提醒。只记录邮箱摘要而非原文；用于限流计数、排查发信失败和避免重复发信，不保存邮件正文或链接原值。 |
| 会话 `sessions` | `id, token_hash, user_id, credential_version, created_at, last_active_at, expires_at, revoked_at`，以及会话列表所需的脱敏设备描述；`token_hash` 唯一，外键指向成员。期限按 `min(last_active_at + 30 天, created_at + 180 天)` 判定（6.3.3），`last_active_at` 每会话最多 24 小时更新一次。不持久化原始 Cookie，也不把原始会话凭证返回列表。 |
| 邀请码 `invitations` | `id, code_hash, issuer_user_id, used_by_user_id, created_at, expires_at, revoked_at, used_at`；码哈希唯一，消费人唯一。`issuer_user_id` 允许为空，只用于本机准备的 bootstrap 码，空 issuer 不代表任何成员。过期由服务端时间计算并按字段派生“有效、已用、作废、过期”，不需要为每个到期码跑定时任务。额度的 `total` / `occupied` 定义见 6.5.2。 |
| 恢复及认证凭证 | `recovery_codes` 记录 `user_id, code_hash, generation, used_at`；`reset_links` 记录凭证哈希、目标成员、签发来源（邮箱找回或管理员）、签发管理员、有效期和消费时间。TOTP 记录加密密文、随机 nonce、密钥版本和最近接受的时间步；通行密钥记录唯一 `credential_id`、公钥、计数器和设备属性。`reset_links` 需能撤销同一目标成员的**全部来源**未用链接，签发邮箱重置链接、签发管理员重置链接以及改邮箱验证成功替换邮箱时都触发，保证任一时刻最多一个有效重置链接。认证库可合并其内部表，但必须保留这些一次性/唯一约束；挑战记录只承担认证所需的临时状态。 |
| 观看进度 `watch_progress` | 主键 `(user_id, playable_unit_id)`；`position_seconds, completed, updated_at, revision`；`revision` 已启用（6.7.1），上报携带 `expectedRevision` 条件写入，冲突返回 `409 / REVISION_CONFLICT`。总时长来自已导入媒体，不相信客户端提交的时长；自动完成与手动“未看”的交互按 6.7.1。 |

- 索引围绕已知查询建立：季的 `(work_id, season_number)`、集的 `(season_id, episode_number)`、媒体/字幕的单元外键、会话的 `(user_id, expires_at)`、邀请的 `(issuer_user_id, created_at)`、成员的邀请人外键、进度的 `(user_id, updated_at)`、片单的 `(owner_user_id, updated_at)` 和条目的顺序键；恢复/重置凭证按哈希查找并按有效期清理，邮箱唯一性用“已占用邮箱”唯一键集合（同时覆盖 `email_key` 与 `pending_email_key`，见 6.0.4 的跨列约束要求）建立唯一索引；邮箱验证凭证按 `token_hash` 查找、按 `(user_id, purpose, consumed_at)` 撤销该成员该用途下的旧 token；`reset_links` 按 `(user_id, consumed_at)` 撤销同一目标的全部来源旧链接；发信记录按 `(to_email_key, purpose, created_at)` 支撑限流计数。仅为中英文作品名搜索按当前规模实现参数化查询，不凭空承诺普通 B-tree 可加速任意子串搜索。

#### 6.2.2 D1 写入与幂等

- 所有用户输入使用预编译参数绑定。迁移按版本管理并在 staging 验证外键和索引；采用 D1 支持的单条条件写入和 `batch()` 事务，不套用跨多次网络调用的交互式 `BEGIN` / `COMMIT`。
- 一次性消费使用类似 `UPDATE ... WHERE used_at IS NULL AND revoked_at IS NULL AND expires_at > now` 的条件，并确认影响行数为 1。**条件更新影响 0 行不会自动让 D1 batch 回滚**：后续写入必须受同一消费结果约束，或由数据库约束使失败分支整批回滚；不能先消费后在 JS 中检查再另写成员/密码。
- 注册时将邀请码消费、成员创建（含邮箱与 `email_verified_at` 为空）、邀请链关联和恢复码哈希写入放在同一原子提交中；消费人的唯一关联和成员的注册邀请码关联需互相校验。邮箱验证 token 的写入与该提交同批完成或紧随其后，但**发信在提交之后**：发信失败不回滚注册，也不能因为邮件没发出去就烧掉邀请码。用户名或邮箱冲突、邀请码抢占失败都不能烧掉邀请码。发码与额度更新、恢复凭证消费与密码更新/旧会话撤销、片单重排与版本更新也遵守同样边界。scrypt 和外部 Turnstile 验证在提交前完成，提交时重新校验必要状态。
- 邮箱验证 token 的消费使用与恢复凭证相同的条件写入语义：`UPDATE ... WHERE consumed_at IS NULL AND expires_at > now` 并确认影响行数为 1，随后在同一批内标记 `email_verified_at`。两个并发点击最多只有一个能把账号标记为已验证；先消费后检查的写法不允许。
- 改邮箱沿用同一提交边界：未验证账号在同一批内替换 `email` / `email_key`、保持 `email_verified_at` 为空，并撤销旧验证 token 与该账号全部来源的旧重置链接。已验证账号申请阶段只写入 `pending_email` / `pending_email_key` 并撤销此前同用途未消费的验证 token，旧邮箱与其找回链接保持有效；新邮箱验证成功时才在同一批内替换邮箱、更新 `email_verified_at`、清空待验证邮箱并撤销全部来源的旧重置链接。任一步失败都不留下部分提交，也不提前改变已验证的旧邮箱。
- 三条恢复路径（恢复码、邮箱重置链接、管理员重置链接）在同一批内消费凭证、更新密码/凭证版本、按 6.4 处理认证设备、撤销该成员全部旧会话、撤销全部旧恢复码，并撤销该成员当前全部来源的旧重置链接；**不签发新恢复码，也不自动建立会话**。已购服务的发信请求在提交之后，发送失败不恢复已撤销的旧链接。
- 发码需要服务端认可的 `operationId`，限定在发出人和操作类型内并设唯一约束，避免网络重试重复扣额；只返回本次生成的原码，不提供事后查询原码的接口。若提交成功但响应丢失，可返回该操作已完成，不能再生成一份替代码或重复扣额。作废与额度返还按 6.5.2 处理。
- 进度、收藏按组合主键条件 upsert；片单修改以 `expectedRevision` 条件写入，成功整体增加版本，失败返回 `409` 及当前版本，不能部分重排。重排需处理位置唯一约束，不能顺序移动时撞上旧位置。
- 权限、封禁、会话撤销和一次性凭证读取走 D1 主库；不启用读副本即可满足这一边界。以后用 Sessions API 时，将合并后的鉴权查询作为 `withSession('first-primary')` 的首次查询，不能把后续可能走副本的独立状态查询当作即时封禁检查。成员状态还需纳入敏感条件写入，避免鉴权后封禁与提交竞争。

### 6.3 身份认证

- 注册必须提供有效邀请码，并提供邮箱。邀请码只能使用一次，可以作废，也可以设置过期时间。
- 注册后账号处于待验证状态，必须通过邮箱验证才能登录成员功能。邮箱验证流程、成员自助修改邮箱、发信通道和限流见 6.0。
- 登录方式是用户名加密码。成员还可以绑定通行密钥（WebAuthn）用于免密码登录，以及开启 TOTP 二步验证。
- **用户名**：长度 3–12 个字符，只允许 ASCII 英文字母、数字、连字符 `-` 和下划线 `_`（`[A-Za-z0-9_-]`）；不区分大小写，唯一性按小写化的 `username_key` 判定，因此 `Picard` 与 `picard` 视为同一账号。展示时按成员填写的原样显示。长度和字符集都在服务端校验，只靠客户端校验不接受。
- **密码**：长度 10–128 个字符，字符范围限定为可打印 ASCII `0x21`–`0x7E`，即**不允许任何空白字符、中文或 emoji**；**不强制大小写、数字或符号的组合要求**，只按长度和字符范围校验。密码**不做自动 trim 或任何规范化**，`a b` 这类含空格的输入是无效输入而不是被静默裁剪。强度由长度和 6.3.1 的 scrypt 参数共同保证。范围与长度都在服务端校验，客户端校验不构成通过条件。
- 密码哈希使用 `node:crypto` 的 scrypt，参数取 N=2^14、r=8、p=5，每次约占 16 MB 内存，强度和 OWASP 推荐的其他参数组合相当。不使用 argon2，因为 Workers 不支持；也不使用 PBKDF2，因为 Web Crypto 在 workerd 中限制迭代次数不超过 10 万次（这个上限是根据运行时行为观察到的，文档里没有写明，开发时需要实测确认）。
- TOTP 密钥在数据库中加密存储，加密密钥放在 Worker Secrets 里。
- 登录、注册、邮箱验证、修改邮箱和恢复接口通过 Workers Rate Limiting 限流，连续失败后要求完成 Turnstile 人机验证。
- 会话存在 D1，浏览器端用 HttpOnly、Secure、SameSite 的 Cookie 保存会话标识。
- 认证实现按 6.3.1 先验证 Better Auth，兼容性验证通过后采用，失败报告站长决定。认证模块保留接入后续 OAuth 的边界，v1 不实现 OAuth；邮件发信按 6.0.3 接入已购服务，不绑定认证库。

#### 6.3.1 凭证与挑战的安全约束

- 密码哈希存储算法版本、上述 scrypt 参数、随机盐和派生值；校验时用常量时间比较。限制输入大小，实测当前 Workers 运行时的 CPU、内存和并发成本，不能因库默认值不同改用其他算法。原文关于 PBKDF2 上限是待实测说明，不作为新平台承诺。
- **认证实现先验证 Better Auth**：先做**最小 POC** 验证本文既定规则能否满足——scrypt 哈希与参数替换、D1 注册（邀请码原子消费）与三条恢复路径的事务、旧会话/旧凭证撤销、Cookie 属性与 `__Host-` 要求、通行密钥（WebAuthn user verification）和 TOTP 规则。**POC 通过后采用该库；失败则把差距报告站长决定。禁止绕过门槛直接自研，也禁止用库默认行为覆盖本文已定规则。** 这是已确认的执行门槛，不表示已经验证通过。
- 密码和 TOTP 登录可分成两个 action：密码通过后只建立短期、单用途、限次数的待验证挑战，不授予完整成员会话；开启 TOTP 的账号完成验证后才建立正式会话。**重新发起密码阶段不得重置 TOTP 的累计失败次数。** **通行密钥与 TOTP 的组合规则已定：用通行密钥登录时验证器已强制用户验证（user verification），不再额外要求 TOTP；用密码登录时，已开启 TOTP 的账号仍必须完成 TOTP。** 敏感操作的再验证要求不因此放宽。
- 通行密钥注册和登录校验服务端随机 challenge、预期 `origin` / RP ID、签名和用户验证要求；challenge 绑定用途及成员/匿名登录流程、带有效期并原子消费。不得把客户端返回的成员 ID 当作账号归属。计数器异常按库支持的 WebAuthn/同步通行密钥语义处理，不能自行规定“计数为零即封禁”。
- TOTP 用带认证的加密保存，建议 AES-GCM，随机 nonce 不复用，附加认证数据绑定成员 ID、用途和密钥版本；密钥不与播放/备份密钥共用。只在绑定时向当前成员展示配置密钥，确认有效验证码后才启用。验证码通过的时间步条件更新，防止相同验证码并发重放。**参数已定：6 位数字、30 秒步长、接受当前时间步及前后各 1 步（容许偏差约 ±30 秒）；登录和再验证的 TOTP 挑战有效期 5 分钟、最多 10 次尝试，成功一次即消费，用过的时间步不可重放。**
- 修改密码、重发恢复码、解绑认证设备以及已验证成员申请修改邮箱需要当前会话和当前凭证的再验证；已开启 TOTP 时不能跳过该步骤。成员会话列表仅返回设备概述、创建时间、有效期及是否当前会话，撤销请求限定 `user_id = 当前成员`。未验证账号改邮箱没有会话，改用 `username` + `currentPassword` 加匿名 CSRF 证明归属，按 6.0.4 执行。

#### 6.3.2 限流与 Turnstile

| 入口 | 限流键与处理边界 |
| --- | --- |
| 登录、注册、恢复（恢复码 / 重置链接 / 邮箱重置）、未验证账号改邮箱的匿名密码校验 | 按**账号或凭证的不可逆摘要 + operation** 计数，每 operation **每分钟 10 次、滚动 15 分钟 30 次**；不存在的账号和邀请码也走同样分支。 |
| 连续认证失败与 Turnstile | 同一账号摘要**连续失败 5 次**触发 `TURNSTILE_REQUIRED`，此后每次认证都要先过挑战。**完整认证成功**（含完成 TOTP 的密码登录）或**连续 15 分钟无失败**即解除。重新发起密码阶段不重置累计失败数。 |
| TOTP 挑战 | 每个挑战单独上限：**5 分钟有效、最多 10 次尝试**，成功一次即消费，时间步重放拒绝。 |
| 播放 token 签发/续期 | 按成员 **每分钟 30 次**。 |
| 管理员高影响操作（ban / unban / quota / role / reset-link） | 按管理员 **每分钟 30 次**；管理员代发邮件不设站内发信频率上限，但**管理 action 本身仍受此限流**。 |
| 验证 token 消费 | 按 token 摘要**每分钟 10 次、滚动 15 分钟 30 次**。 |
| 正常媒体与字幕的 GET / HEAD / Range | **不消耗**上述任何配额。 |
| 验证邮件、重发验证、改邮箱验证、邮箱找回发信 | 按目标邮箱的不可逆摘要和用途执行 6.0.3 的 60 秒间隔、滚动 60 分钟最多 5 次；注册验证、重发验证与改邮箱验证共用配额，找回单独计数。超限不发信；找回对存在与不存在邮箱返回相同响应和相同计数。 |
| 管理员代发重置邮件、封禁安全提醒 | 不设站内发信频率上限；服务商自身限额仍适用，失败不回滚管理操作。 |

- 上表的额度用 **D1 精确累计和滑动窗口**实现，Workers Rate Limiting 只作辅助降本，不能承担配额判定。计数状态存 D1 并条件累加/清零，不只依赖某个 isolate 或 IP；匿名状态有过期和大小边界。
- 触发 Turnstile 后接口返回 `TURNSTILE_REQUIRED`。提交的 `turnstileToken` 必须服务端调用 Siteverify，并核对当前环境的 hostname、操作 action 和成功结果；过期、重复使用或错环境拒绝。验证依赖不可用时返回可重试错误，不绕过挑战，也不把临时故障计为密码错误。
- 限流命中返回 **`429` 并带 `Retry-After`**，前端按 code 处理。邮箱存在与否不改变响应和计数。所有上表数值纳入 6.9.1 的集中配置。

#### 6.3.3 会话期限、活跃与改密

- 会话有两个上限，取先到者：自登录起**绝对最长 180 天**（按会话创建时间算，不因活跃而延长），以及**连续 30 天不活跃即失效**。两者都到期或任一先到时会话失效，需要重新登录；已过期的会话不能靠任何请求续回。
- **活跃的定义很窄：只有成功的成员 HTML 页面 / 页面 loader 访问算活跃。** 播放 token 签发与续期、媒体与字幕 Range、字幕轨、进度上报、收藏与片单等 API action、后台任务、预取和直接 HTTP 数据请求都**不续期**，也不刷新活跃时间。
- `last_active_at` 每个会话最多每 24 小时更新一次，避免每次页面访问都写库。因为存储的是**上一次**更新时刻、而不是真实的最后活跃时刻，判定可能比真实的 30 天**提前最多约 24 小时**到期；这是可以接受的方向，宁可略早失效也不延长会话。
- Cookie 期限与 `min(last_active_at + 30 天, created_at + 180 天)` 保持同步。**不按每次访问 rotate Cookie**，也不改动 `__Host-` 前缀要求的既有安全属性（`HttpOnly; Secure; SameSite=Lax; Path=/`、不设 `Domain`）。
- 成员正常改密码时**保留当前会话、撤销该成员的其他全部会话**，并为当前会话**换发新的会话标识**（旧标识立即失效）。换标识时**保留原会话的创建时间和已算出的期限**，不能借此重置 180 天的绝对上限，也不重新开始 30 天活跃计时。
- 6.4 的三条恢复路径仍按各自规则**撤销全部旧会话**并返回正常登录，不适用本节的“保留当前会话”。

### 6.4 账号恢复

- 第一层：成员注册或开启二步验证时，系统生成一组一次性恢复码（默认 10 个），只保存哈希值。成员可以用任意一个恢复码重设密码。
- 第二层：成员用注册邮箱自助找回——提交邮箱后收到一次性重置链接。这是 v1 新增的常规找回路径，见 6.0.2。
- 第三层：恢复码全部丢失、邮箱也不可用时，管理员在后台生成一次性重置链接（默认 24 小时有效），通过站外渠道交给成员，也按 6.0.3 代发通知邮件。
- 三条路径并存，不互相替代，都能独立走通。通过恢复码重设密码后清除已开启的 TOTP 验证器，保留已绑定的通行密钥；通过管理员重置链接恢复账号后，同时清除 TOTP 和通行密钥，成员需要重新绑定。
- 通过邮箱重置链接重设密码**只改密码**：保留已开启的 TOTP 验证器和已绑定的通行密钥，因为这条路径的前提就是成员仍能收到该邮箱的邮件。代价是它解决不了验证器遗失的问题——遗失 TOTP 验证器时仍需恢复码或管理员重置链接，邮箱路径不承担这个职责。
- 三条路径在恢复成功后都撤销该成员的全部旧会话，也**撤销该成员当前全部来源的旧重置链接**（含邮箱找回和管理员签发的未用链接），避免已寄出的旧链接被重放。
- 三条路径在恢复成功后都**撤销该成员全部旧恢复码**，并且**不自动签发新一组恢复码**。成员用新密码正常登录后，在账号页按 6.3.1 的再验证要求手动重新生成默认 10 个恢复码。
- 恢复成功后**不自动登录**，统一返回正常登录，由成员用新密码自行登录。邮箱验证成功同样不自动登录（6.0.1）。
- 再次签发重置链接（邮箱找回或管理员代发）都撤销该账号所有来源的旧链接，任一时刻最多一个有效重置链接，默认 24 小时有效；**发信失败也不恢复已撤销的旧链接**。
- 被封禁成员不能通过任何一条路径解除封禁。

#### 6.4.1 一次性恢复的提交边界

- 恢复码和重置链接由密码学安全随机数生成，数据库只存哈希；查找和校验不输出原值。恢复码在注册、启用二步验证或重新生成时，仅在本次成功响应中展示；重新生成时原子撤销该成员的**全部**旧组，不能让两组同时有效。三条恢复路径成功时同样撤销全部旧组，且不签发新组（6.4）。
- 恢复 action 提交 `username, recoveryCode, newPassword`，或 `resetToken, newPassword`，需要 CSRF，达到阈值时还需 `turnstileToken`。验证新密码后，在一个事务内消费凭证、更新密码/凭证版本、按 6.4 处理认证设备、撤销所有旧会话、撤销全部旧恢复码并撤销全部来源的旧重置链接；两个并发请求最多一个成功。恢复码恢复也采用此旧会话撤销约束，不把恢复当作普通已登录改密。
- 重置链接 loader 仅验证流程并渲染表单，不能在 GET 时消费凭证，避免链接预览器烧掉它。浏览器地址中的凭证不写日志、不进入 Referer、不缓存，表单页不加载会携出链接的第三方资源。
- 被封禁成员不能通过恢复解除封禁或获得有效会话。恢复按 6.4 已定规则处理认证设备并撤销全部旧会话；普通改密按 6.3.3 保留当前会话、撤销其余会话，恢复后不自动登录、恢复码签发和旧链接撤销均已按 6.4 确认。

### 6.5 邀请与权限

- 角色只有两种：成员和管理员。
- 未登录时可访问访客首页 `/`、关于页 `/about`、登录 `/login`、邀请码注册 `/register`、邮箱验证落地 `/verify-email`、等待验证提示页、邮箱找回 `/forgot-password`、恢复码找回 `/recover` 和一次性重置入口 `/reset/:token`；恢复、重置和邮箱验证操作仍须校验相应凭证。改邮箱验证的落地页沿用 `/verify-email`；待验证账号可在未登录状态下用 `username` + `currentPassword` 提交改邮箱（6.0.4），这条匿名路径不因此开放其他受保护页面或数据。公开静态素材遵循 6.1 的约定。
- 访客首页和关于页不展示海报、作品列表、片库统计、成员数据或讨论，访客不能打开会列出作品的搜索。直接访问受保护页面时跳转 `/login?next=…`，登录后返回原页面；相关数据和媒体接口在服务端独立校验权限。
- “站内公开”的片单仅向已登录成员公开；仅片单所有者可以修改或删除该片单。评论、回复和赞踩只允许有效成员读取或操作，作者和管理员身份由服务端确定。
- 管理员生成邀请码不受数量限制。普通成员的邀请额度按 6.5.2 的定义计算。
- 封禁一名成员时，可以选择只封禁他本人，或者沿邀请链连带封禁他邀请的人。封禁后该成员的所有会话立即失效，后续成员接口操作（含评论、回复和赞踩）被拒绝，已经签发的播放 token 最多 30 分钟后自然失效。
- 解除封禁是 v1 提供的独立管理员操作（故事 74），规则见 6.5.3。
- 封禁生效后向被影响成员的注册邮箱发送安全提醒邮件（故事 70）。通知邮件里只说明账号状态变化，不含讨论内容、片库资料或其他成员的邮箱/身份信息。发信失败不影响封禁本身的原子提交，封禁结果以服务端状态为准，不因邮件问题回退或部分回滚。

#### 6.5.2 首个管理员、邀请额度与连带边界

- **首个管理员不通过网页注册产生**：站长用普通邀请码注册并完成邮箱验证后，在本机用运维命令把该账号提升为管理员。**不开放 first-admin 网页注册入口**，也不提供通过注册参数把自己设成管理员的路径。
- 首个邀请码由本机初始化准备，`issuer` 可以为空。空 issuer 只用于这类 bootstrap 码，**不得假冒任何业务成员**，也不会出现在成员列表或邀请链的“邀请人”列里。
- 管理员完成高影响管理操作前需要绑定 TOTP；未绑定时引导先绑定（6.5.1）。

- **邀请额度定义**：每位普通成员有 `total`（默认 `2`）和派生的 `occupied`。`occupied = used + validUnused`，即已使用数加有效未使用数；`available = total - occupied`。**生成邀请码即占用**；使用后永久占用，不因使用后的到期或成员封禁返还；**仅未使用码**作废或过期时释放占用。**没有周期补额**。
- 管理员为成员调整 `total` 时，**不得低于当前 `occupied`**；低于则拒绝并返回当前占用数，不截断既有邀请码。
- 邀请码**默认有效期 30 天**，可在生成时显式指定其他期限。
- 邀请码的“已过期”由签发时记录的到期时间派生，**不需要为每个到期码跑定时任务**；读取和校验时按当前服务端时间计算即可。

- **邀请码发出人被封禁时，其名下的有效未使用邀请码全部作废并释放占用**。注册与封禁在同一 D1 原子提交边界内重新校验：注册先提交时，只有 `cascade=true` 才将新普通后代纳入本次连带封禁；只封本人时新成员保持正常。封禁先提交时，两种模式均拒绝消费已被作废的邀请码。不能留下漏封后代或孤立邀请链。
- **连带封禁覆盖全部普通后代**：沿邀请链向下，封禁所有普通成员后代；**遇到另一个管理员即为边界**——该管理员本人不被这次封禁波及，其后代也不再继续向下连带。自封禁、末位管理员保护按同一原则适用（6.5.3）。

#### 6.5.3 管理员边界与解除封禁

- **网页端禁止管理员封禁自己或取消自己的管理员身份**，也不能让系统中的正常管理员数量归零。这条用 D1 条件写入在并发下保护：请求与状态变更在同一个原子批次内重新校验，条件更新影响 0 行即失败，不先读后写。
- 站长在本机做紧急处理（例如需要恢复站点可用性）属于**本机运维操作**，不经过网页端，也不受上述网页规则约束；本机工具的具体设计随 6.8 的离线工具确定，不在此扩展。
- **解除封禁**（故事 74）是独立的管理员 action：
  - 只能对**当前处于封禁状态**的成员执行；目标不存在或未被封禁时按统一语义拒绝。
  - **不连带解封**，只恢复这一个人。
  - **不恢复旧会话**，也不恢复已作废的邀请码；被解封的成员自己重新登录。
  - 邀请总额度 `total` 保持原值，`occupied = used + validUnused`，`available = total - occupied`；已用码仍永久占用，不能因解封返还。
  - **解封不额外发送通知邮件**；除上述已列规则外，本条不新增其他通知、撤销或连带行为。

#### 6.5.1 权限矩阵与 HTTP / loader / action 草案

站长是拥有管理员权限的运维者，不增加第三种业务角色。下表路径是后端接口命名草案，页面路径可随前端路由确定；身份和错误语义不能随路径调整而改变。公开“站内片单”仍需登录，公开恢复入口仅用于凭证恢复，不公开任何片库或账号资料。

### 6.6 播放与媒体分发

- v1 直接播放 MP4 文件，要求视频为 H.264、音频为 AAC，并做 faststart 处理（元数据放在文件开头，这样不用下载完就能开始播放和拖动）。不做 HLS，也不做在线转码。
- 成员打开播放页时，Worker 签发一个播放 token：
  - 用 HMAC 签名，内容包括成员 ID、会话、可播放单元、媒体文件 ID 和过期时间；
  - 有效期 30 分钟，播放页在到期前 5 分钟自动续期；
  - 续期和每次媒体请求都检查成员与当前会话状态，所以被封禁、退出或会话被撤销后最迟在 30 分钟内无法继续播放。
- token 放在媒体地址的查询参数里，因为 `<video>` 标签无法自定义请求头。Worker 验证 token 后，把浏览器的 HTTP Range 请求原样转给 R2，并返回 `206 Partial Content`。
- 字幕文件用**同一个播放 token** 访问，范围限于该可播放单元下已挂接的 VTT 字幕轨（6.6.1）。
- 播放器使用 ArtPlayer，支持外挂 VTT 字幕及中文、英文、关闭三档切换；键盘操作包括空格播放或暂停、方向键快进快退和音量、`F` 全屏、`M` 静音、`C` 切换字幕。
- 播放页提供上一集、下一集、当前季选集、手动标记已看或未看和加入片单。播完后显示下一集提示和可取消的倒计时；倒计时结束或点击立即播放时进入下一集并尝试播放，浏览器阻止自动播放时保留手动播放入口。没有下一集时不显示无效操作。从片单进入的播放按 6.7.2 继续队列，不在队列结束后回退到剧集自然下一集。
- 切换可播放单元时，读取该成员对目标单元的进度；没有记录则从头播放，不得沿用上一集的起点或把上一集的进度写入新单元。
- v1 不限制每个账号的同时播放数。以后要加这个功能，入口放在 token 签发和续期这一步，限额由管理员在后台随时调整。

#### 6.6.1 token 载荷与撤销边界

- token 使用 HMAC-SHA-256，格式草案为 `base64url(payload).base64url(signature)`；签名覆盖带用途前缀的载荷原始字节，不重新序列化后验签。载荷包含 `v, kid, environment, purpose, userId, sessionId, credentialVersion, playableUnitId, mediaFileId, iat, exp`，`purpose` 固定为 `playback`，`exp - iat` 不超过已定的 30 分钟。`kid` 只从服务端允许的密钥版本集合选取，不接受客户端指定算法或密钥来源。
- `environment` 和用途前缀防跨环境/跨协议重用；每个环境的签名密钥独立。载荷不包含 R2 bucket、key、URL 或明文会话 token；ID 可读，签名并不加密载荷。
- 严格限制 token 长度和解码结构，拒绝不认识的版本、错误用途、异常时间及多余的重复 query 参数；以固定长度的签名字节用常量时间校验，不用字符串 `===`。验签通过前不查 R2、不向响应泄露对象元数据。
- 成员绑定在资源入口核对请求者的服务端身份，不能用请求体/query 的成员 ID 代替；请求者未登录或 token 的成员与请求者不同均拒绝。
- **媒体与字幕共用同一个播放 token（已确认）**：视频和该单元下**所有已挂接的 VTT 字幕轨**都用同一个 token 访问，因此取消按资源分别签发专用 token 的方案，载荷不再要求 `resourceType` 区分媒体与字幕。签发时该单元只允许一个 v1 MP4，token 绑定 `playableUnitId` + `mediaFileId` + 当时的 `userId` / `sessionId` / `environment`。
- 授权边界：媒体只授权载荷指定的 `mediaFileId`；同一 `playableUnitId` 下已挂接的 VTT 字幕轨允许共用 token。替换为其他媒体文件或其他单元的字幕 ID 时拒绝，不限制同单元中英文字幕之间的切换。
- **每次 GET / HEAD / Range 都做即时鉴权（已确认）**：同源媒体与字幕请求同时携带当前 Cookie，载荷带 `sessionId, credentialVersion`，服务端合并从 D1 主库检查会话未过期/未撤销、成员状态正常、成员与 `sessionId` 匹配且 `credentialVersion` 一致。退出、撤销会话、三条恢复、封禁后，**下一个媒体请求即拒绝**。不缓存鉴权结果，不使用只读 replica；另一成员即使登录也不能使用复制的 token。
- 一次已开始的流不会因数据库改动自动收回已发出的字节。实现必须在 token 到期时停止继续输出并取消 R2 读取，避免无 Range 的长响应越过“封禁后最多 30 分钟”的上限；到期前签发的续期不延长旧流的截止时间，新的签发/续期重新检查状态。即时鉴权只影响新请求，已开启的流最晚仍在旧 token 到期时停止，30 分钟上限不变。

#### 6.6.1.1 播放 token 续期策略

- 播放页在 token 到期前 **5 分钟**请求同一签发 action 续期，接口重新鉴权并返回新的 token 与 `expiresAt`。
- 网络错误或 `503` 按 **5 秒、15 秒、30 秒**退避自动重试，**最多 3 次**；`401` / `403` **立即停止**续期并转登录或提示，不再重试。
- 到期前始终没有续期成功时，播放器**暂停并提示手动重试**，不静默停播，也不无限重试。
- 续期成功换上新授权后，要**保留播放位置、暂停/播放状态和字幕选择**，不得因为换 URL 而从头播放。
- 开发时用两小时以上的连续播放验证拖动、字幕切换和续期换 URL 的实际表现；不能假定换 URL 一定无缝，不能用短片段可播代替（见第 7 节）。

#### 6.6.2 R2 与 HTTP Range 契约

鉴权先于 HEAD、Range 判断、条件响应和任何 R2 读取。Worker 使用私有 R2 binding，将资源 ID 映射到 D1 中的对象键，不重定向到 R2，也不返回可绕过 Worker 的预签名地址。

| 请求 | 外部行为 |
| --- | --- |
| `GET` 无 Range | `200 OK`，流式返回整文件，`Content-Length` 为对象总字节数，不带 `Content-Range`。到 token 截止时间取消尚未发送的流。 |
| `GET` 单个有效字节范围 | 支持 `bytes=start-end`、`bytes=start-`、`bytes=-suffix`，把原始 Range 头交给 R2 的 ranged read，不能先取全文件再切片；返回 `206`，以实际返回范围计算头和长度。end 超出尾部时截断到文件末尾。 |
| 范围无法满足 | start 超出文件、反向范围或零长度 suffix 返回 `416 Range Not Satisfiable`，`Content-Range: bytes */total`，无媒体 body；总大小仅在授权通过后可见。 |
| 非法 Range / 未支持的范围形式 | 格式不合法返回 `400`；非 bytes 单位和有效的多范围请求在 v1 忽略 Range，按无 Range 返回 `200`，不声称支持 multipart，也不拼成错误的单段 206。 |
| `HEAD` | 经过相同授权，忽略 Range，`200` 返回完整 GET 的元数据和总长度，没有 body；用 R2 `head()`，不为了 HEAD 拉取视频内容。 |
| `If-Range` | 不能直接假定 R2 支持；Worker 校验 ETag/时间条件，匹配才保留 Range，否则返回完整 `200`。v1 可不实现其他条件缓存响应；任何条件响应都不能绕过鉴权。 |
| 文件缺失 / 方法不支持 | 缺失返回脱敏 `404`，记录资源 ID 供排查；其他方法返回 `405` 及 `Allow: GET, HEAD`，不开放浏览器上传。 |

- 成功响应设 `Accept-Ranges: bytes`；206 的 `Content-Range` 为 `bytes start-end/total`，`Content-Length = end - start + 1`。R2 对象 `size` 是总大小，不当作部分 body 长度；依据返回的 `range` 核对实际范围，不仅依据请求的 end。
- MP4 使用 `video/mp4`，字幕使用 `text/vtt; charset=utf-8`；字幕接受同样的资源鉴权和 GET/HEAD 规则。只复制允许的 R2 HTTP 元数据，再覆盖安全/缓存头，不能让上传的 `cacheControl` 变成公开缓存。
- R2 `body` 以流交给响应；增加截止时间/取消处理时也不能整体 `arrayBuffer()` 或缓存进内存。媒体不压缩、不改写字节，不能让 Content-Length 与 Range 语义偏离；客户端断开时取消上游读取。
- v1 不将授权媒体响应放进共享 CDN/Cache API；query token 和 Cookie 不能成为“忽略查询参数缓存”的入口。签发结果、200、206、416 和错误均按私密缓存边界处理。日志/追踪必须剔除 query 的 `token`、恢复凭证和 R2 下载地址；按当前官方文档，默认 invocation log 会记录请求 URL，若不能脱敏则关闭该项并保留白名单应用日志，部署前验证实际日志。

### 6.7 观看进度与片单

- 播放页定期上报播放位置（默认 15 秒一次），暂停和离开页面时也上报一次。进度存在 D1，按“成员 + 可播放单元”保存，所以换设备也能接着看。
- 播放位置达到总时长的 90% 就标记为已看完（默认值，可调）。成员也可以手动标记。
- “继续观看”显示成员最近看过、还没看完的可播放单元。如果一集已经看完，就推荐同一部剧的下一集。首页与作品页采用一致的续播规则，手动标记和按作品去重不得让仍有未完成记录的作品消失。
- 收藏只针对作品。片单是有序列表，条目可以是作品或单集，成员可以设为私有或站内公开。
- 成员可以创建和删除自己的片单，添加、移除或调整条目顺序；桌面提供上移和下移，触屏支持滑动排序，移除入口保留给键盘和读屏用户。
- 片单提供“按顺序播放”入口，正式版须按 6.7.2 的展开规则构建播放队列，不能替换成剧集的自然下一集。

#### 6.7.1 写入与读取约束

- 上报位置必须是有限非负数，不能超出服务端已知总时长；手动已看/未看与自动上报明确区分，不能把缺省 `completed` 当作手动“未看”。看完阈值读取集中配置。
- 所有进度、收藏及片单写入以当前成员限定 ownership。站内公开片单只返回片单及作品/单集概要，不带所有者的私人进度；私有片单不能通过条目 ID 绕过权限。
- **进度采用 `expectedRevision`（已确认启用）**：请求携带 `expectedRevision`，服务端条件写入并返回新的 `revision`；版本不匹配返回 `409 / REVISION_CONFLICT` 和当前 `revision`。
- 冲突后的客户端行为**已定**：拿到 `409` 的旧上报**直接丢弃，不自动重放**。只有用户继续观看产生新的播放事件时才发下一次上报，客户端**不做无限补报队列**。同时不采用“取位置最大值”，因此**正常回看到更小的位置可以正常保存**。
- **手动“标记未看”已定**：`positionSeconds` 归 `0`、`completed = false`，并让 `revision` 递增。已落库后的旧上报因版本不符被拒绝；此后用户真实观看重新达到 `90%` 阈值即可再次标记完成，**不存在长期的手动覆盖状态**。
- “下一集”按同一作品的季号、集号排序查询；只有实际已导入可播媒体的单元才能返回播放地址。跨季、缺集时如何提示仍由前端按既有产品行为处理，不伪造不存在的片源。

#### 6.7.1.1 片单条目去重

- **同一目标在一个片单内只能有一条**（唯一键为 `playlist_id` 加目标类型与目标 ID）。重复添加同一目标时**返回已存在的那一条**，不新增条目、**不改变它的顺序**；接口返回的仍是成功结果，客户端据此刷新列表。
- 作品条目和它下属的单集条目**允许同时存在**，这是两个不同目标；播放队列仍按 6.7.2 在展开后按可播放单元 ID 去重。
- 去重要靠数据库唯一约束 + 条件写入实现，**并发重复添加必须幂等**：并发请求最终只留一条，另一条返回同一已有条目，不产生重复行或顺序抖动。

#### 6.7.2 “按顺序播放”的队列展开

- 队列按片单条目的存储顺序逐条展开：
  - 电影作品条目对应该电影的可播放单元；
  - 单集条目对应其自身；
  - 剧集作品条目展开为该作品下按季号、集号排序的、已导入且可播的集。
- 展开后按可播放单元 ID 去重，同一单元只保留第一次出现的位置，后续重复项丢弃。
- 展开结果中已看完的单元被跳过，不进入播放队列。
- 未看完的单元从该成员自己的保存进度开始；没有进度记录时从头播放，不沿用队列中上一单元的起点。
- 若全部可播单元均已看完，停留在片单页并提示“已全部看完”，不进入播放页、不自动重播。
- 队列播放时，队列内下一个单元优先于剧集的自然下一集；队列到达末尾后不再使用剧集的自然下一集。
- 队列播完后停止，不继续自然下一集，也不循环回队列开头；停留在当前播放页，显示“片单已播放完”和返回该片单的入口。
- 队列展开后的按单元去重，只作用于播放队列结果；**写入侧**按 6.7.1.1 禁止同一目标重复条目。

### 6.8 离线导入工具

这是一个在站长本机运行的命令行工具，可以指定导入到 staging 还是 prod。它负责：

- 读取 manifest，建立作品和季的记录；
- 按 TMDB ID 拉取作品、季和集的中英文资料；
- 检查 MP4 的编码和 faststart 是否符合要求，不符合就报错，提示站长先在本地转码；
- 把字幕统一转成 VTT，其中 ASS 字幕会丢失样式；
- 上传媒体文件和字幕文件到 R2，并在 D1 中写入对应记录。

导入可以重复执行而不产生副作用：记录以 TMDB ID 或季号、集号为唯一键，已经存在的文件会跳过。网站本身不提供内容管理后台，TMDB API Key 只放在站长本地。

#### 6.8.1 输入、预检与断点重试

- 输入契约由明确的 `environment`（仅 `staging` / `prod`）、仓库 manifest 和本机媒体映射组成。媒体映射声明 `kind, tmdbId`，集再声明 `seasonNumber, episodeNumber`，以及仅本地使用的 `videoPath`、字幕 `language, displayName, trackKey, sourcePath`；不靠文件名猜作品或集号，不把本机绝对路径存入 D1。工具启动时展示目标环境并校验资源归属，缺配置或身份歧义立即停止，不能默认写 prod。
- manifest 约束 v1 可导入作品和季；季条目的 `tmdb_id + season` 映射到所属剧和季号，再从 TMDB 获取季/集身份。电影和剧集分别使用其 TMDB 类型，不以标题匹配。manifest 的 `file` 是 `.jpg` 原图名，页面海报引用必须映射到仓库中存在的 `.webp` 静态资产；本项目海报留在 public，素材 README 中“生产导入 R2”的旧描述不改变 6.1 决策。
- 上传前完成本地预检：MP4 容器有效、视频 H.264、音频 AAC，解析容器确认 `moov` 位于媒体数据 `mdat` 前而非仅看扩展名；记录时长、字节数和 SHA-256。失败给出具体文件与原因并提示先转码，工具不在线转码，也不自动上传不合格文件。
- 字幕先按既有规则转为 VTT，再验证 UTF-8、`WEBVTT` 头、cue 时间语法、开始不晚于结束、时间可解析和标签/文本可安全渲染；ASS 转换明确提示样式丢失，不能把 ASS 原文件发布给 v1 播放器。语言限中文/英文，同一轨道用稳定 `trackKey` 识别。
- TMDB key 仅从站长本机环境变量 `TMDB_API_KEY` 读取，禁止写进输入文件、上传清单或 Worker Secrets。中文缺失保留为空并回退英文，不能把两种文本覆盖为同一列；上游超时/限流可重试，不把失败写成成功的空资料覆盖已有记录。
- 顺序为“预检及身份确认 → 上传并验证完整 R2 对象 → D1 原子挂接记录”。D1 和 R2 没有跨产品事务；上传过程中不修改现有可播记录，不能让 D1 引用未完成对象。大文件 multipart 的 upload ID、分片进度及校验值保存在本机断点记录，完成后才发布；失效上传重新开始并处理未完成分片。
- 使用稳定逻辑唯一键和服务端生成的私密对象键防重复。本机检查发现 D1 与 R2 的长度/校验均吻合时跳过；R2 完整但 D1 未提交时可校验后补挂接，D1 存在而 R2 缺失时只补缺文件。相同身份却不同校验值必须报冲突，不能以“幂等”名义覆盖旧可播内容；替换既有媒体不在本次导入规则内。
- D1 提交失败时，v1 只保留完整且可验证的对象供重试，不在失败路径自动删除对象。如需清理，必须暂停导入并排除并发挂接后另行操作，不能仅凭一次“无引用”检查删除对象。中断后从本机记录和 D1/R2 实际状态重建进度，不相信单一“已上传”标志。最终报告已导入/已跳过/冲突/失败的逻辑 ID 和数量，不输出凭证或远端私密路径；私密路径仅存在本地配置、内部 D1/R2 数据，不进公开仓库或浏览器。

### 6.9 环境与备份

- staging 和 prod 是两套完全独立的资源，各自有自己的 Worker、D1 和 R2。
- D1 利用 Time Travel 功能，可以恢复到最近 30 天内的任意时间点。
- 一个 Worker 定时任务（Cron Trigger）每天调用 D1 的导出 API，把导出文件存进 R2 的备份目录，再加密后用 HTTP `PUT` 推送到 Cloudflare 之外的一个 WebDAV 地址。导出内容包含密码哈希和 TOTP 密钥，所以必须加密后才能离开 Cloudflare。备份默认保留 30 天。
- WebDAV 地址必须能从公网通过 HTTPS 访问，最好用 443 端口。如果它在家里的 NAS 上，推荐用 Cloudflare Tunnel 暴露出来，不需要在路由器上开端口。
- Cloudflare API Token、WebDAV 账号密码和备份加密密钥都存在 Worker Secrets 里。
- 视频原片只在站长本地冷备份，不存第二份云端副本。

#### 6.9.1 绑定、Secrets 与集中配置

每个环境分别配置下列逻辑名称，实际资源标识和值不写入公开仓库。本项目统一使用 `cf` CLI 创建项目、本地开发、部署和管理 Cloudflare 资源，不再使用 Wrangler，也不以 `npx wrangler` 替代。执行前先查 `cf --help` 或 `cf cli search <想做的事>`，确认命令、参数和目标环境；如引入已有 Wrangler 配置，按 `cf migrate` 的当前帮助迁移。`cf` 缺失、不支持所需能力或命令失败时记录原因并告知站长，不自行回退到 Wrangler，不在本文猜写 CLI 或配置方式。

| 类别 | 建议名称与用途 |
| --- | --- |
| Worker bindings | `DB`：本环境 D1；`MEDIA_BUCKET`：本环境私有 R2（媒体、字幕和备份按逻辑用途隔离）；`ASSETS`：公开静态资源；`AUTH_RATE_LIMITER`、`PLAYBACK_RATE_LIMITER`、`ADMIN_RATE_LIMITER`、`EMAIL_RATE_LIMITER`：按确认后的限流策略配置，其中 `EMAIL_RATE_LIMITER` 仅用于 6.0.3 的成员发信（注册验证、重发验证、改邮箱验证、邮箱找回）的辅助防滥用；成员配额由 D1 精确判定。管理员代发重置邮件和封禁安全提醒不经站内发信限流，管理 action 仍按 6.3.2 限流。staging/prod 不共享 Rate Limiting namespace/counters。 |
| Worker 配置 | `APP_ENV, APP_ORIGIN, WEBAUTHN_RP_ID, TURNSTILE_SITE_KEY`，以及**发信服务的发件人地址与发件域名、邮件服务商 API 基础地址**、备份目标数据库标识、Cron 调度和兼容日期；真实 Cloudflare 标识只保存在本机/平台配置，缺失或混用环境时拒绝运行。发件域名需按服务商要求配置 SPF/DKIM（必要时的 DMARC），staging 与 prod 用不同的发件人标识以便区分测试邮件。`node:crypto` 支持按选定兼容日期核实，不能只凭 Vitest 自动兼容通过就认定生产可用。 |
| Worker Secrets | `PLAYBACK_HMAC_KEY`：播放签名；`TOTP_ENCRYPTION_KEY`：TOTP 认证加密；`TURNSTILE_SECRET_KEY`：服务端挑战验证；`EMAIL_API_KEY`：发信服务的 API 凭证（按 6.0.3 通过 HTTPS 调用）；`CLOUDFLARE_API_TOKEN`：备份导出所需的最小权限；`BACKUP_ENCRYPTION_KEY`：备份加密；`WEBDAV_URL, WEBDAV_USERNAME, WEBDAV_PASSWORD`：HTTPS PUT 目标和凭证。认证库确有要求时再增加 `AUTH_SECRET`，不得与其他密钥复用。`EMAIL_API_KEY` 只用于发信，不给它任何读信、读账号或其他产品面的权限。 |
| 仅站长本机 | `TMDB_API_KEY`、目标环境资源映射和离线导入所需的最小权限 D1/R2 凭证；不把导入管理能力做成浏览器接口，不给 Worker 播放路径额外的上传管理 token。 |
| 集中默认配置 | 邀请额度 `2`、恢复码数量 `10`、重置链接有效期 `24 小时`、邮箱验证链接有效期 `24 小时`（注册验证与改邮箱验证共用）、看完阈值 `90%`、进度上报间隔 `15 秒`、备份保留 `30 天`、评论正文上限 `1000 字`、评论每页 `10 条`、回复每批 `10 条`、播放 token `30 分钟` 集中维护。已确认的限流数值同样纳入：登录/注册/恢复/匿名改邮箱/邀请码/凭证摘要**每 operation 每分钟 10 次、滚动 15 分钟 30 次**；连续失败 `5 次` 触发 Turnstile、解除条件为完整认证成功或 `15 分钟` 无失败；TOTP 挑战 `5 分钟` / `10 次`；播放 token 每成员 `30 次/分钟`；管理员高影响操作每管理员 `30 次/分钟`；验证 token 消费每摘要 `10 次/分钟` 与滚动 `15 分钟 30 次`；成员发信 `60 秒` 间隔与每用途滚动 `60 分钟` `5 次`；会话绝对 `180 天`、不活跃 `30 天`、`last_active_at` 粒度 `24 小时`；TOTP `30 秒` 步长与 `±1` 步容差。 |

**密钥轮换（已确认）**：**手动轮换，不设定期自动轮换**。每个环境的密钥**相互独立**，同一密钥不复用于不同环境。保管方式为三处：线上 Worker Secrets、站长的密码管理器、以及**离线副本**。旧密钥必须**保留到引用它的全部备份都被删除或重加密之后**才能弃用，**包括受保护而超期保留的最后一份副本**；**缺密钥的备份不算可恢复副本**。

本机 `.dev.vars` 使用前确认已被 git 忽略；样例仅用占位符。密钥版本随密文/token 保存，轮换时不能先丢弃解密材料。

#### 6.9.2 每日备份执行与失败行为

- **调度时间已定**：每日**北京时间 04:00**（即 **UTC 20:00**）触发，由部署时配置 Cron 表达式到该时刻；不是由调用方或自动化临时触发。允许 **04:00–04:15** 期间存在导出带来的维护和查询影响，这个窗口对成员可见属已知代价。
1. 每日 Cron 在本环境发起全量 D1 SQL 导出，包括 schema 和全部业务数据；导出无法通过普通 D1 binding 替代。当前官方 API 是 `POST /accounts/{account_id}/d1/database/{database_id}/export`，首次使用 `output_format: 'polling'`，之后以返回的 bookmark 填入 `current_bookmark` 持续轮询同一任务，直至完成或失败；不能伪造同步 dump API。
2. 导出期间数据库可能无法服务查询，持续轮询中断时平台会取消导出。不得将仍在执行的导出留到第二天 Cron 才继续。完成后及时读取返回的短期 `signed_url` 并流式存入私有 R2 备份对象；不能把下载 URL 返给浏览器、写日志或交给 WebDAV 抓取。
3. R2 记录本次备份 ID、环境、备份时间、导出 bookmark、schema 版本、长度和 SHA-256；只有完整写入并校验后才标记 R2 完成。备份控制状态可放在私有 R2 元数据/伴随记录，不因此追加业务表；重试复用已验证的备份 ID，避免重复导出和混淆日期。
4. 从 R2 加密后用 HTTPS `PUT` 推送 WebDAV。采用带版本的认证加密封装（建议 AES-GCM；若分块，每块独立唯一 nonce、认证序号/总块数，并验证最终完整性）；大小不得要求整个 SQL 常驻内存，采用有界缓冲/流处理。目标只能来自 Secret，不跟随把授权头带到其他主机的重定向。**只有 R2 完成、加密完整、WebDAV 上传成功并回读校验通过后，才记录“备份完整成功”。**
5. **上传后回读校验（已确认）**：`PUT` 成功后再用 HTTPS `GET` 把对象**流式读回**，校验**长度和 SHA-256** 与本地记录一致。**ETag 不能代替内容哈希**校验。回读可能耗时，按实际耗时在 staging 实测并纳入 15 分钟时限评估（6.16）。
6. 导出/R2/WebDAV 任一失败都不创建成功标记：保留完整 R2 副本和**脱敏失败记录**，由站长**人工触发重试**。**不设置自动重试调度，也不做主动失败告警。**
7. **保留策略**：默认保留 `30 天`，但**每一端（R2 与 WebDAV）的最后一份完整可恢复副本受保护、可超过保留期不被删除**。清理绝不触碰媒体对象，备份与媒体清理前缀严格隔离；清理失败可重试，不把部分失败当作已删除。

每日 Cron 当前最长执行时间为 15 分钟，导出轮询、加密、PUT 和回读校验的全流程都要在这 15 分钟内实测；必须整体由 scheduled 生命周期等待，不依赖 HTTP 返回后 30 秒的 `waitUntil`。必须在 staging 测量备份大小、耗时和内存；若全流程装不进单次时限，**报告站长**决定调度或恢复办法，**不擅自引入 Queues、Workflows 或其他新产品**。

#### 6.9.3 手动恢复顺序与完整性

1. 站长选择正确环境及恢复点，**先暂停该目标的写入和导入，并保留当前状态所在的旧库**（不先删、不先覆盖），再执行恢复。
2. **默认恢复目标是隔离的 D1 目标**：先恢复到隔离目标并完成校验，通过后才切换。**Time Travel 的隔离能力不作假定**——按官方现有能力核实后再决定；**若无法构建隔离目标，如实报告站长，不自行对生产库做原地覆盖恢复。**
3. 优先按事故选择 Time Travel 或完整备份。WebDAV 副本须验证密文认证、备份元数据、长度和校验，先在 Cloudflare 内解密到私有对象再导入；不在本机下载未加密 SQL，不让包含密码哈希/TOTP 数据的明文副本离开 Cloudflare。
4. SQL 恢复使用当时官方支持的导入流程。当前 D1 REST import 为 `init → 上传 SQL → ingest → poll`，参数和临时地址以官方响应为准；上传及轮询在 Cloudflare 内完成，不能把 SQL 文本交给站长本机 CLI 作为中间明文文件。在隔离目标确认 schema 兼容、外键完整、业务计数与摘要一致后，再执行目标切换。
5. 验证 `media_files` 和字幕关联的 R2 对象确实存在且长度/校验匹配；**恢复 D1 不会恢复 R2 媒体，也不会恢复 Worker Secrets**。缺媒体时需从站长本地冷备及字幕原件重新导入；尚未补齐的文件保持不可播，不先开放错误地址。
6. **重新开放前统一撤销**（已确认）：旧会话与旧播放/媒体 token、**未使用的邀请码**、**全部恢复码**、**全部重置链接**、**全部验证链接**一律作废，成员必须重新登录。撤销凭证版本时须**同时切换到可信的外部密钥版本**，避免恢复点把 `credentialVersion` 倒退。**密码与认证设备（通行密钥、TOTP）按已校验的恢复点原样保留**——恢复可能带回恢复点之后已解绑的设备，重新开放前由站长知悉并复核。
7. **角色与封禁状态由站长逐条复核**；无法确认的账号保持**维护状态**而不是直接放行。
8. **邀请码**：恢复出的全部未使用码撤销后，`validUnused = 0`，`occupied = used`，`available = total - used`；已用记录仍占额度，不因恢复返还（6.5.2）。
9. **旧讨论（已确认做法）**：恢复点中的历史评论和回复**照原样恢复**，不做自动识别或自动清理。维护期间由管理员**人工 review 并重新手动删除**需要移除的内容。**不引入隐藏标记、软删除、删除 ID 台账，也不批量清空正常讨论**；**接受无法自动识别全部历史删除**这一事实，**不宣称历史备份或恢复点已被擦除**。

平台行为核对于 2026-10-04，开发时按实际兼容日期再核实：[D1 batch / Sessions](https://developers.cloudflare.com/d1/worker-api/d1-database/)、[外键](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)、[R2 ranged read / If-Range 边界](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)、[Rate Limiting 一致性](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)、[node:crypto](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/)、[D1 export](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/)、[D1 import](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/import/)、[Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)、[Workers 执行时限](https://developers.cloudflare.com/workers/platform/limits/)、[URL invocation logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)。

### 6.11 页面与跨页面交互

- 视觉方向、基础 token、版式和响应式验收遵循 6.14；本节规定页面内容与跨页面交互。
- 访客首页在桌面展示星图和标题栏，在小于 768px 的视口展示登舰指南。星图属于装饰，不要求位置具备考据准确性；手机指南包括欢迎语、邀请码入口、加入三步、成员能力、守则和常见问题。首页的邀请码输入传递到注册页，成员登录提供通行密钥入口和密码登录链接。
- 关于页包括本站介绍、如何加入、成员守则、隐私与数据、找回账号、版权说明和技术说明；宽屏提供本页导航。版权说明保留《星际迷航》版权归 Paramount 所有的声明，并展示站长接收下架请求的公开联系邮箱 `contact@startrekchina.org`（这是站长自己的联系方式，不是 Paramount 官方渠道）。该邮箱只作展示，不引入邮件登录或站内发送系统。
- 成员首页以影院式舞台展示当前作品、单集、简介、海报、进度和继续播放入口；刻度尺展示其他继续观看条目及上次观看时间或“下一集”。点击未选中条目切换舞台，点击已选中条目播放；超宽条目可以横向滑动。新成员无观看记录时展示三个推荐起点，由站长通过配置文件维护，不增加网页管理功能；首版依次为 SNW、TNG、TOS 的第一季第一集，调整随部署生效。配置映射到正式片库的可播放单元，原型 ID 仅作参考。
- 剧集和电影页提供海报网格与按首映年份排列的时间轴两种视图，均可进入同一作品页。作品页保留资料、收藏、加入片单、季切换、逐集观看状态和单集剧照；中文资料缺失时回退英文。
- 成员搜索支持中文和英文作品名，并可用 `Ctrl+K`、`⌘K` 或 `/` 打开；`D` 切换深浅色。手机底部提供搜索和菜单胶囊、回到顶部按钮。访客菜单不展示受保护入口或作品搜索结果。
- 页脚提供跟随系统、浅色和深色三档主题选择；导航、页脚和页面内容在不同宽度下保持对齐。手机的固定导航、底部安全区、顶栏和播放器控件不得遮挡关键操作。
- 保留原型中账号页的宽屏分节导航、季选择和长列表的滚动提示、复制按钮、异步操作反馈及 404 页面。按钮、弹层、滑动条目和表单需要保留键盘和读屏可用性；文本输入时字母快捷键不触发站点操作。系统开启减少动态效果时，跳过平滑滚动、淡入和高亮动画。
- 原型中的数据刷新即重置、签发 token 文案和模拟加载不能作为正式行为；持久化、凭证校验、加载失败和重试应由正式前后端共同完成。

### 6.12 播放页讨论

#### 6.12.1 位置与对话

- 每个可播放单元有独立讨论区。单集放在选集列表下方，电影放在简介下方，标题分别为“本集讨论”和“本片讨论”，显示讨论总数；无内容时显示空状态。
- 1024px 及以上采用双栏：左栏为发评论输入框和评论列表，右栏为当前评论、回复及固定在对话底部的回复框。默认选择第一页第一条评论，点击评论空白处或回复数量可以切换对话，点击正文链接或选择文字不触发切换。
- 右栏按原型吸顶并内部滚动，标题和回复框保持可见；小于 1024px 时改为单栏，点击回复数量在评论下方展开或收起对话。
- 回复按时间正序排列。回复某位成员时显示“回复 @用户名”，可点关闭按钮取消；空回复框按 `Esc` 返回回复评论作者。点回复时聚焦输入框，并滚动到不被顶栏和底部导航遮挡的位置。
- 显示作者、当前成员和管理员等原型标签，长正文可以展开或收起。评论时间保留原型的等宽英文格式：7 天内用相对时间，更早用日期，跨年加年份；悬停显示完整时间。

#### 6.12.2 输入、发送和草稿

- 评论和回复正文上限默认 1000 字，提供工具栏、表情、Markdown 速查、预览和字数反馈。Markdown 支持粗体、斜体、删除线、代码、引用、列表、链接和分隔线，回车换行；不支持图片、表格和 HTML。
- 站外链接新窗口打开并带 `nofollow ugc`，同时防止新页面控制原窗口；`//host` 视为站外，`javascript:` 等危险协议不生成可点击链接。限制不能仅依赖前端编辑器，服务端须验证正文及长度，渲染须避免注入脚本。
- 发送按钮和 `Ctrl+Enter` / `⌘Enter` 使用相同行为。发送期间显示状态，锁定输入、工具栏、表情和预览以防重复提交；状态通过 `role=status` 向读屏播报。
- 发新评论后保持当前排序和正在看的对话，把新评论置顶并提示其位置；新回复展开到末尾并滚动到可见位置。系统启用减少动态效果时不闪烁或平滑滚动。
- 各对话的未发送草稿独立保存，切换对话或跨越宽窄屏断点不丢失。发送途中切换对话时，回复仍发送到原目标，返回时保持其发送状态；只有发送成功才清空对应草稿，失败时保留内容并允许重试。跨设备或刷新后的草稿同步不由本条要求。

#### 6.12.3 赞踩、排序与分页

- 评论和回复支持赞或踩，再点同一反馈取消，切换反馈替换原反馈。赞显示数量，踩不显示数量、仅参与智能排序；服务端保证一名成员对同一对象最多一个当前反馈。
- 评论提供智能、最新、最早三档排序；智能排序沿用原型按赞踩置信度与讨论参与度计算的规则，以原型为算法参考，不引入作品评分功能。选定排序时形成稳定列表，赞踩不会立即打乱当前阅读顺序。
- 评论默认每页 10 条，回复默认每批 10 条。评论和回复关联、数量、作者、时间及赞踩结果持久化到 D1；刷新或换设备后仍可读取。
- 管理员删除评论与回复已纳入 v1，规则见 6.12.4。成员自助编辑或删除、举报、其他审核与恢复工具、剧透遮罩和评论时间码跳转仍在范围外，不因删评纳入而自动加入。

#### 6.12.4 管理员删除评论与回复

- v1 只提供管理员删除评论和回复的入口，不提供成员自助编辑或删除、举报，以及审核/恢复后台。
- 删除顶层评论时，在同一次原子提交中从当前业务数据库移除该评论、其全部回复，以及评论和这些回复的赞踩记录。正文和记录一起删除，不保留软删除标记、删除占位或正文归档。
- 删除单条回复时移除该回复及其赞踩记录，不删除顶层评论或其余回复。回复仍是同一对话中的平铺列表，不另建嵌套回复树。
- 被删内容不再出现在列表、对话或直接读取接口中，也不计入讨论数量、回复数量、智能排序或分页。访问已删除目标，以及向其发送回复或赞踩，返回脱敏 `404`。
- 删除成功后，当前页面移除对应评论或回复；若当前选中的对话已被整段删除，清除其展示和回复入口，按剩余内容更新计数及分页，不留下删除占位。
- 删除与新增回复、赞踩并发时，不得留下孤立回复或反馈：删除前已经提交的关联记录一并移除，删除后提交的新回复或赞踩因目标不存在而失败。删除批次失败时不得留下部分删除的对话，也不得报告成功。
- 封禁成员默认保留其已有讨论记录，不因封禁自动删除评论或回复。
- 服务端按 6.5 的权限与归属校验执行删除，并沿用统一的 CSRF 校验；删除接口不能绕过认证、管理员权限或可播放单元归属检查。
- 上述删除范围是当前业务数据库和站点读取。删除前的备份及 D1 Time Travel 恢复点**仍可能含有旧数据**，不能把业务记录删除宣称为历史备份已被擦除。**恢复点中的历史讨论照原样恢复**（6.9.3），这类情况由管理员在维护期间**人工 review 并重新手动删除**；不引入隐藏标记、软删除或删除 ID 台账，也不清空正常讨论。

## 7. 测试决策

- 只测试从外部能观察到的行为：请求发进去，看返回的结果和数据库、存储里的变化。不测内部函数的调用方式和实现细节。
- 已有正式工程的 Workers Vitest runner、D1 约束与 HTTP 测试，以及前端基础浏览器验收；覆盖进展见 PLAN.md，不表示全部业务已实现。测试边界包括 Worker HTTP 接口、离线导入工具和浏览器中的用户流程；正式开发应将原型行为与本文规则转为可观察的验收，模拟身份或内存数据通过不代表后端已验证。
- 测试边界一：Worker 的 HTTP 接口。用 Cloudflare 的 Workers Vitest 集成在本地运行真实的 Worker，D1 和 R2 使用本地模拟。覆盖以下场景：
  - 注册：邀请码的各种状态（有效、已用、作废、过期），以及额度用完的情况；邮箱必填、格式校验、邮箱冲突不消耗邀请码。用户名 3–12 位 `[A-Za-z0-9_-]`、长度越界和非法字符被服务端拒绝，大小写不同的同名注册冲突且不消耗邀请码；密码 9 位和 129 位被拒绝，含空格、中文或 emoji 的密码被拒绝，不因 trim 而变成合法输入；不满足大小写/符号组合的合法密码仍可通过。
  - 邮箱验证：验证链接成功、过期、重放、并发消费仅一次成功；重发后旧链接失效；重发受限流约束；密码找回对存在与不存在的邮箱返回相同响应；未验证账号无法登录或读取片库；发信失败不回滚注册和邀请码消费。验证成功不建立会话，只返回正常登录；注册验证 token 不能用于消费改邮箱验证，反之亦然。待验证账号长期不验证也不被清理、用户名和邮箱仍被占用、邀请码不返还，只能在配额内重发。
  - 登录：密码、通行密钥、TOTP 分别登录，限流是否生效，Turnstile 何时触发。已开启 TOTP 的账号用密码登录仍需 TOTP；已绑定通行密钥的账号用通行密钥登录（验证器已强制用户验证）不再额外要求 TOTP，但敏感操作仍需再验证。
  - 会话期限与活跃：会话创建满 180 天后即使天天访问也失效；超过 30 天不访问后失效且不能靠请求续回；只有成员 HTML 页面 / 页面 loader 访问刷新活跃时间，播放 token 签发与续期、媒体与字幕 Range、进度上报等 API 请求不刷新也不续期；`last_active_at` 每会话最多 24 小时写一次，因此失效判定可能比真实最后活跃时间提前最多约 24 小时；Cookie 期限与 `min(last_active_at+30 天, created_at+180 天)` 同步且不逐页 rotate，`__Host-` 安全属性不变。正常改密后当前会话仍可用但标识已换发、其余会话全部失效，且换标识不重置 180 天上限与剩余活跃期限。
  - 恢复：用恢复码重设密码（清除 TOTP、保留通行密钥），用重置链接恢复账号（同时清除 TOTP 和通行密钥），用邮箱重置链接重设密码（只改密码，TOTP 和通行密钥都保留），三种方式恢复后旧会话是否全部失效；三者都撤销全部旧恢复码且不签发新组，成员需用新密码登录后在账号页手动生成 10 个新码，恢复码恢复和管理员重置恢复后能否用新密码完成登录而不被遗失的 TOTP 阻挡，邮箱恢复保留的 TOTP 仍需原验证器；被封禁成员不能借邮箱重置解封。
  - 恢复链接唯一性：邮箱找回和管理员签发都撤销该账号全部来源的旧链接，任一时刻最多一个有效链接；恢复成功后旧链接全部失效，重放返回脱敏失败；签发后发信失败也不恢复旧链接。
  - 修改注册邮箱：未验证账号用 `username` + `currentPassword` 提交新邮箱后直接替换为未验证状态并重新发信，密码错误被拒绝；已验证账号在当前会话加再验证（TOTP 开启时需 TOTP）后进入待验证，新邮箱验证成功前旧邮箱和旧邮箱找回仍可用、现有会话不被撤销、角色与其他数据不变；新邮箱验证成功后原子替换并撤销全部来源的旧重置链接，旧邮箱寄出的重置链接不能再夺回账号；新邮箱与他人邮箱或他人待验证邮箱冲突时被拒绝；发信失败保留已完成的变更并允许按配额重发；新申请替代此前未完成的申请，旧验证 token 立即失效。
  - 封禁：只封本人和连带封禁两种方式，封禁后续期播放 token 是否被拒绝。连带封禁覆盖全部普通后代，遇到另一个管理员即停止且不继续其后代。管理员的 ban、unban、quota、role、reset-link 五项缺 TOTP 证明、证明过期、超过 10 次尝试、绑定到其他管理员/会话/操作/目标、已消费后重放，均被拒绝；未绑定 TOTP 的管理员收到引导绑定而不是放行。删除评论与回复只校验管理员会话与 CSRF，不要求 TOTP。
  - 解除封禁：只对被封禁成员成功，不连带恢复其后代；旧会话仍无效、已作废邀请码不恢复，成员重新登录后 `available = total - used - validUnused`，已用邀请码仍占额度；目标未被封禁时按统一语义拒绝；缺 TOTP 证明被拒绝。
  - 管理员边界：网页端自封禁、自降权和使管理员数归零的请求一律被拒；两个并发请求不能把管理员数降到 0。本机提升首管的流程不被网页端注册参数绕过。
  - 播放 token：签名被篡改、已过期、拿去访问别的文件、属于别的成员，这些情况都应该被拒绝。按 6.6.1 验证同一 token 可访问该单元的媒体与全部 VTT 字幕轨，但换成其他可播放单元的媒体或字幕即被拒；退出、撤销会话、三条恢复、封禁后，下一个 GET/HEAD/Range 请求即被拒绝；已开始的流最晚在旧 token 到期时停止，30 分钟上限不变。续期按 6.6.1.1：到期前 5 分钟发起，网络错误或 503 按 5/15/30 秒重试且最多 3 次，401/403 立即停止，到期仍未成功则暂停并提示手动重试。
  - Range 请求：返回 206 状态码，内容范围和字节数正确。
  - 观看进度和片单：增删改查、跨成员隔离、私有与站内公开权限、条目排序，以及“已看完”的判定逻辑；切集不得串用起点，手动标记后继续观看不得漏掉仍未完成的作品。按 6.7.1 验证 `expectedRevision`：版本不符返回 409 且旧上报被丢弃、不自动重放，只有继续观看产生的新事件才再上报；回看到更小的位置能正常保存；手动“未看”后位置归零、`completed = false`、版本递增，此后重新观看达到 90% 仍能自动完成。按 6.7.1.1 验证同一目标重复添加返回已有条目、不新增也不改顺序，并发重复添加幂等，作品与其单集条目可同时存在。另按 6.7.2 验证队列展开（作品与单集混合、去重保留首次出现、跳过已看、无进度从头）、全部已看时的“已全部看完”提示，以及队列播完停在当前播放页并显示“片单已播放完”和返回入口。
  - 评论、回复和赞踩：正文与长度校验、所属可播放单元和对话正确、持久化、每成员单一赞踩及取消、数量、分页和稳定排序；访客与被封禁成员不能读取受保护讨论或发送内容，危险 Markdown 和链接不能造成脚本执行。管理员删除顶层评论后，该评论、全部回复和相关赞踩在数据库及读取结果中均不存在；删除单条回复只移除该回复和其赞踩，不影响其余讨论。被删内容不留占位、不计入数量、排序或分页，直接读取、回复或赞踩已删目标返回 `404`，普通成员调用删除被拒绝。并发写入和删除失败不得留下孤立记录或部分删除。
  - 访问控制：访客可以查看 6.5 列明的公开页面和公开静态素材；访问成员页面时跳转登录并保留返回目标，访问受保护数据或媒体接口时被拒绝。公开页不展示片库、成员记录、搜索结果或讨论，所有页面均禁止索引。
- 测试边界二：离线导入工具。用一份精简的样例 manifest、几个很小的样例视频和字幕文件，导入到本地的 D1 和 R2。验证数据是否正确写入、连续导入两次结果是否一致，以及格式不对的视频是否被拒绝。
- 测试边界三：邮件发信。把已购发件服务的 HTTPS API 换成本地模拟服务，验证发信请求的收件人、正文来源和一次性凭证是否符合 6.0，投递失败、超时和返回错误码时注册、找回和改邮箱流程的行为，以及同一邮箱的限流计数。每次操作最多向模拟服务发出一次请求，失败或超时后无自动补发；超时不报告确定未送达。注册验证、重发验证与改邮箱验证共用验证用途配额、邮箱找回单独计数，各自至少间隔 60 秒、滚动 60 分钟最多 5 次，首次及失败/超时尝试均计入，换 IP 不绕过，窗口边界和并发请求不得超额；管理员通知不受站内发信频率限制，上游拒绝仍记录且不回滚管理操作。手动重发仍遵守相应限流与一次性凭证约束。测试不向真实服务商发信，不使用真实邮箱地址。
- 浏览器验收：覆盖当前原型的全部产品页面，以 1440×1000 桌面和 360×800 手机为基础，检查浅色/深色、成员/访客/管理员、空数据、加载、失败和成功状态；手机视口模拟之外，实际手机的键盘、触控和播放能力也需验证。
  - 访客入口：星图和登舰指南切换、邀请码带入注册、受保护页面登录返回、关于页版权声明与 `contact@startrekchina.org` 下架联系方式展示、无索引规则。
  - 浏览与首页：影院舞台与刻度尺、无记录时按配置展示三个推荐起点（首版 SNW/TNG/TOS 第一季第一集，调整随部署生效）、网格和时间轴、中文/英文搜索、切季、剧照缺失和加载失败占位、观看状态、收藏和加入片单。
  - 播放：真实自生成测试媒体的拖动、字幕、键盘、暂停和离开上报、逐单元续播、跨设备读取、下一集倒计时取消与自动播放受限回退；长时播放按 6.6.1.1 验证续期换 URL 后仍保留播放位置、暂停/播放状态和字幕选择，不能用短片段可播代替。
  - 片单：创建和删除、混合条目增删、桌面按钮和手机滑动排序、可见范围、按 6.7.2 的队列规则播放（含跳过已看、去重、全部已看提示、队列播完停留并提供返回片单入口）。
  - 讨论：宽屏双栏吸顶与窄屏内联展开、空状态、三档排序、评论分页和回复分批、赞踩、Markdown 和预览、键盘发送、回复目标取消、分对话草稿、发送锁定与失败重试、发送途中切换对话、减少动态效果；另验证顶层评论及全部回复整段消失、单条回复删除不影响其余讨论、当前对话关闭和计数分页更新；列表和对话不留删除占位，已删目标不能继续读取、回复或赞踩。
  - 跨页面与账号管理：主题、手机导航不遮挡操作、复制反馈、搜索和主题快捷键不干扰输入、键盘和读屏操作、恢复码保存、账号安全、邀请码状态、邀请链、封禁和管理员操作。管理员页另有解除单个成员封禁的入口与 TOTP 引导，自封禁和自降权在界面上不可用。账号页另有成员修改邮箱流程：已验证成员提交新邮箱后的待验证提示、验证完成后的替换反馈，验证期间照常使用旧邮箱找回；未验证账号的匿名改邮箱提交在手机端也可用。
- 限流（测试边界四）：在 Workers 集成里验证 6.3.2 的全部数值。同一账号或凭证摘要按 operation 每分钟第 11 次、滚动 15 分钟内第 31 次返回 `429` 并带 `Retry-After`；连续失败第 5 次后要求 Turnstile，此后每次认证都需先过挑战，完整认证成功或连续 15 分钟无失败后解除；重新发起密码阶段不重置 TOTP 累计失败；TOTP 挑战自身 5 分钟 / 10 次上限独立生效；播放 token 每成员第 31 次/分钟与管理员高影响操作每管理员第 31 次/分钟被拒；验证 token 消费每摘要第 11 次/分钟被拒；正常媒体与字幕的 GET、HEAD、Range 不消耗任何配额；邮箱存在与不存在的响应和计数一致。
- 备份定时任务：把 WebDAV 目标换成本地模拟服务，验证上传的内容是加密的、可以正常还原，且 PUT 之后流式 GET 回读的长度与 SHA-256 与本地记录一致（构造 ETag 相同但内容不同的对象，确认不会被误判为成功）。另验证保留清理保留每一端最后一份完整可恢复副本、可超过 30 天，且绝不删除媒体对象。

### 7.1 后端补充验收条件

沿用外部可观察行为的边界，HTTP 集成使用 `@cloudflare/vitest-pool-workers` 的真实 Workers 运行时和本地 D1/R2；只观察请求、响应、数据及对象状态，不断言内部函数调用。涉及 6.16 验证门槛的用例在门槛完成前不宣称通过，本地模拟不宣称验证了线上复制延迟、Rate Limiting 全局精度或实际导出耗时。

| 片单播放队列 | 按 6.7.2 验证电影、单集和剧集混合条目的顺序展开；按单元 ID 去重且保留首次出现；跳过已看，未看完的从本人保存进度开始，无进度从头。全部已看时留在片单页提示“已全部看完”，不自动重播。队列内下一项优先于剧集自然下一集；队列播完停在当前播放页，显示“片单已播放完”和返回片单入口，不继续自然下一集、不循环。 |
| token | 篡改、到期、未来异常时间、错环境、错 `purpose`、错文件/字幕/单元、另一成员请求均拒绝；同一 token 可访问该单元的媒体与全部已挂接 VTT 字幕轨，但不能跨到其他可播放单元。签发/续期拒绝封禁或失效会话；每次 GET/HEAD/Range 都做主库即时鉴权，退出、撤销会话、三条恢复、封禁后下一个请求被拒；GET/HEAD 未授权不暴露文件大小/类型。已开启的流最晚在旧 token 到期时停止，跨到期的流不能继续输出。续期提前 5 分钟，重试 5/15/30 秒最多 3 次，401/403 立即停止，到期暂停并提示手动重试。 |
| 进度与片单 | 上报携带 `expectedRevision` 条件写入并返回 `revision`，版本冲突返回 409 且旧上报不被自动重放；回看到更小位置能保存；手动“未看”归零并递增版本，之后重新观看达到 90% 可再自动完成。同一片单内同一目标重复添加返回已有条目、不新增不改顺序，并发重复添加幂等，作品与其单集条目可并存；跨成员隔离和私有片单权限仍然生效。 |
| Range | 对已知字节夹具验证完整 200、HEAD 无 body、闭区间/开放尾/后缀 206、end 截断、尾外/反向/零后缀 416、错误语法 400、多范围/非 bytes 回退 200 和 If-Range 不匹配回退；逐项核对 body 字节、`Content-Range`、`Content-Length`、`Accept-Ranges`、类型和私密缓存头。字幕同样验证授权。 |
| 公开入口与访问控制 | 访客可直接访问 `/`、`/about`、`/login`、`/register`、`/verify-email`、`/forgot-password`、`/recover`、`/reset/:token` 的表单流程，以及静态海报和剧照；无效/已用/过期重置链接和验证链接按凭证规则反馈，GET 不消费。公开页面、loader 和搜索入口不泄露片库、成员记录或讨论；成员首页数据及其他受保护页面/数据接口不可匿名读取。待验证账号与访客受到相同的片库访问限制，但其按 6.0.4 提交的匿名改邮箱请求仍须校验 CSRF 与当前密码，且不能借此读取其他账号数据。 |
| 首页推荐 | 无观看记录成员的首页 loader 返回站长配置的三个推荐起点，首版为 SNW、TNG、TOS 第一季第一集；配置映射到正式片库的对应可播放单元，调整随部署生效，不增加网页管理入口。 |
| 评论、回复与赞踩 | 访客和被封禁成员不能读取或写入讨论；替换单元/评论/回复 ID 不能跨单元提交。正文上限、受限 Markdown、危险链接、持久化、数量、分页和稳定排序符合 6.12；并发赞踩仍仅一个当前反馈，重复设定或取消返回最终状态且不重复计数，不向浏览器返回踩数量。管理员删除按 6.12.4 验收：仅管理员可删，顶层评论、全部回复及相关赞踩在同一原子提交中移除，单条回复删除只影响该回复及其赞踩；数据库不保留被删正文或软删除记录。读取结果、数量、智能排序和分页不含被删内容，不显示占位，直接读取或向已删目标回复、赞踩返回 `404`；普通成员及错单元删除请求被拒绝。并发回复或赞踩不得留下孤立记录，失败批次不部分删除。封禁不自动删除已有讨论；恢复点中的历史讨论按 6.9.3 原样恢复并由管理员人工复核重删，不引入软删除或删除台账。 |
| 响应与隐私 | 直接请求受保护 loader 数据/action 也须认证；跨站 action/CSRF 失败；公开资产、错误、重定向、媒体均 noindex；robots 禁止全部。浏览器响应不含内部 R2 key/URL 或 Worker Secrets；验证发码/恢复码签发、TOTP 绑定及播放签发仅向有权接收者返回必要一次性凭证、绑定材料或短期授权地址，列表、无关响应和错误不带凭证原值或完整 token。捕获日志始终不含凭证原值、完整 token（包括 query token）、内部 R2 key/URL 或 Worker Secrets；默认平台 URL 日志在 staging 单独检查。 |
| 导入 | ffmpeg 生成小片段，合法/错误 codec、非 faststart、损坏 MP4、非法 VTT 分别验证；manifest 季身份、JPG→WebP 映射和双语回退正确；两次导入无重复。注入上传中断、R2 已完成/D1 失败、D1 有记录/R2 缺失和校验冲突；D1 提交失败后完整对象仍保留，不触发自动删除，重试只补缺，不破坏旧片源/并发引用。 |


备份测试用本地模拟 Cloudflare export/import 与 WebDAV HTTP 服务，只用虚构成员；生产未加密备份不能用于本机测试。部署前在 staging 另验 D1 导出生命周期/维护影响、Cron 时限、实际内存、scrypt 运行时、限流绑定和日志配置，不能用本地通过替代这些平台验证。当前已有正式工程、D1 迁移及 Workers Vitest runner，已运行的工程基础用例见 PLAN.md；备份、完整业务和平台验收尚未执行，原型及素材测试不能代替正式后端验收。
