# 请求级身份与 D1 往返优化（2026-10-13）

本地已实现请求级身份复用、认证包装去重和媒体查询合并，完成自动化自检。T4.5 尚未整体验收：[2026-10-14 staging 复验](staging-revalidation-20261014.md)确认 D1 优化与核心安全/日志检查通过，但播放页及续期的 R2 串行校验带来端到端回退，性能与站长确认仍待完成。本文保留本地测量口径，云端数据以新报告为准。

## 基线与方法

- 起始版本：`dev` 的 `0fa22842b6503e9b4020500b7dd833703dd3aa96`；核心实现通过 `perf/request-identity` 交付至 `dev`，当前云端复验版本为 `cbb16db`。对应代码摘要、24 个前后对比场景及 3 个补充场景的本地计数和脱敏调用时间线见[测量数据](performance-request-identity-20261013.json)。
- 使用锁文件安装依赖，Better Auth 1.7.7；真实 workerd、隔离的本地 D1/R2，虚构的 3 部作品、2 季、2 个可播放单元、1 个 MP4 和 1 条字幕。测试准备、账号创建、迁移不计入请求预算。
- 测量时 `APP_ENV=development`，与既有运行配置一样关闭重复 schema 检查；其余自动化继续按原测试配置验证 schema。没有关闭 Cookie、CSRF、限流或成员门禁。
- 测试直接调用实际 Worker `fetch`，替换该请求的 D1 binding 为透传探针；同时覆盖原生认证和业务 SQL，包含 `withSession()`、`batch()`、`all/first/run/raw`。prepare/bind 不计执行次数，batch 计一次 API 调用、多条 SQL。
- 保存每次执行的开始/结束、分类、可得的 duration/rows read/rows written，不保存 SQL、参数、Cookie、邮箱、token、媒体地址或对象键。`first/raw` 不返回执行元数据，相关指标标为不可得；本地 duration 常为 0，不解释为云端无耗时。
- 相同场景先在原实现上运行，预算断言因重复查询失败，再运行修复。首次播放 SSR 和 `.data` 均为 15 次 D1 调用，Range 为 6 次，会话接口为 7 次。随后对固定基线补齐完整场景，结束后逐字节恢复修复代码。

下面是调用数，**不是线上毫秒收益**。每个场景当前只有一个保存的本地样本；响应创建耗时不等于浏览器 TTFB。重叠调用不求和，库耗时不能再叠加其包含的 D1 等待。库内部的完整 CPU/包装耗时、线上中位数/P95 和容量尚未测量。

“原生会话读取”根据锁定 adapter 的会话 SQL 分类计数，不把本站最终授权 JOIN 算成第二次原生解析。无 Cookie 时没有 D1 查询；并行匿名解析一次由独立 Promise/调用断言验证。

播放页关键链原来为：基础身份 3 次调用 → 片库 batch → 第二轮身份 3 次 → liveMember JOIN → 片源 → 配额 → 字幕，共 11 个串行 D1 阶段；root 的另一轮身份和统计与子 loader 重叠。现在是共享基础身份 3 次 → 片库 batch → 片源/字幕 batch → 最终配额写入，共 6 个阶段；root 统计仍可并行。Range 原来 6 个串行调用，现在 4 个。完整起止区间在测量数据中，不将 SSR 父子 loader 的重叠等待直接相加。

补充的最终实现样本：管理员额度写入为 6 次调用，未验证成员为 3 次并拒绝；本人会话撤销为 10 次（4 次原生 session SELECT）。撤销包含本站身份 3 次、目标 ID→token 归属读取 1 次、原生权威身份 2 次、原生目标会话/用户归属 2 次、deleteWithHooks 删除前查询 1 次及 DELETE 1 次。初始试探预算漏计删除钩子的 SELECT，且探针曾把 DELETE 误计为读取；核对锁定源码后校正分类和这一新增场景预算，未修改既有验收用例。该路径未减少库内部查询。

## 实现与保留的工作

1. Worker 每次 fetch 创建懒加载上下文，显式传入所有成员 loader、业务 HTTP 入口及内部 Request 克隆。并行调用共享首次 Promise，成功、匿名、失败均不重复解析；每个新请求独立判断。既有直接调用测试未提供上下文时，每次调用创建新上下文，仍可模拟下一请求，没有使用 Request 对象地址作为缓存键。
2. 原生会话读取之后，一条主库 JOIN 同时读取成员并重新确认会话仍有效；播放原有的独立 liveMember 查询由这一判断覆盖。媒体最终查询继续核验实时会话、邮箱、注册状态、封禁及资源归属。
3. `/get-session` 直接使用原生端点结果再做成员门禁；已登录二步与受保护端点通过公开 `getSession` API 使用当前库上下文，不再另建认证实例。锁定版本的 sensitive middleware 会主动清空上下文并执行 authoritative 读取，这些查询保留。本人会话撤销仍由原生端点执行，其权威身份及目标归属读取没有绕过；新会话建立前后的门禁仍保留。
4. Cookie 收集与身份 Promise 分开，每个调用方得到独立 Headers，实际响应出口按名称合并。原生新发/清除会话优先于早先续期；本人当前会话撤销明确清除 Cookie，状态变更后失效请求快照。没有让服务端身份进入 loader DTO。
5. 签发的 MP4/字幕读取放入一个 batch，恰好一个 MP4、字幕顺序及 token 期限保留；配额条件写入同时检查会话与片源，失败时区分权限、片源与配额。视频授权片源和元数据合并；字幕同时验证绑定 MP4 和轨道关系。R2 head、大小/ETag、Range/If-Range、到期和断开取消保持原实现。
6. 片库现有 batch、紧凑 DTO 和当前作品范围继续复用。详情多出的作品卡片查询用于相邻作品入口，不能当作重复身份查询删除；没有改写片库/管理业务 SQL，也没有新增索引、跨请求缓存、依赖或通用监控框架。管理员最终 SQL 权限、自保护、幂等及配额条件保留。

库接口依据以本机锁定包的 `api/routes/session.mjs`、`api/dispatch.mjs`、二步插件源码和集成测试为准。公开资料参考：[D1 batch 与会话](https://developers.cloudflare.com/d1/worker-api/d1-database/)、[Better Auth 会话](https://better-auth.com/docs/concepts/session-management)。

新增竞态用例确认：在原生会话读取与成员 JOIN 之间撤销、在成员读取与媒体最终查询之间撤销、在片源读取与配额提交之间删除会话或片源，均拒绝；不会把失败当游客成功，不泄露媒体元数据，不错误地报告配额耗尽或扣额。管理员身份读取后被降权，既有条件写入以冲突拒绝，目标额度不变。已有套件继续覆盖封禁、改密新会话、备用码、通行密钥 UV、注册失败、CSRF、末管保护及配额并发。

浏览器使用当前工作树的 `cf dev`，监听 `0.0.0.0:6120`，仅专用虚构账号和自生成媒体；标签在“性能修复验证”组。未登录 `/series` 回跳登录并保留目标，建立登录态后实际点击电影链接产生 `.data` 导航，页面和账号标识均更新；虚构作品详情显示正确季/集与播放入口。本地 Turnstile 控件未返回响应，登录态通过官方测试 token 和真实用户名登录接口建立，未改变服务端验证；不将此计作登录表单或真实人机挑战验收。首次加载播放器依赖曾出现 Vite 旧 React 模块错误，重载后重新核对，重载并对隐藏标签启用临时焦点模拟后，自生成 4 秒 MP4 完整播完，readyState=4、无解码错误、中文字幕可见；定位到第 2 秒成功。真实 Range 返回 206/128 字节，退出接口返回 200，随后原媒体 HEAD 返回 401 且不含 Content-Length。其他扩展弹窗关闭后，补验退出后访问片库回到 `/login?next=%2Fseries`、页面标题为“登录”且不显示成员菜单；临时焦点模拟已关闭。
