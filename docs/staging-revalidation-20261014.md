# staging 性能、安全与日志复验（2026-10-14）

## 结论

**签发链可避免的 R2 串行等待已修复，并通过 staging 同条件对照；历史尾延迟尚未解释，T4.5 与第四阶段保持未验收。** 请求级身份与媒体查询优化确实减少 D1 往返，首次多提交对照中的回退同时包含必要的媒体实时校验成本和不必要的串行等待。仅并行独立 HEAD、保留全部安全条件后，播放页 HTML、数据请求及续期的 TTFB 中位数分别降低 25.8%、24.6%、23.8%。安全与日志检查在各自注明的范围内通过，不代表全部性能或功能验收。

### 回退原因

播放页和签发/续期的 D1 等待区间并集确实缩短，但 Worker 响应创建时间上升。补充 R2 探针确认：当前授权增加 1 次视频 HEAD，再并行执行 3 次字幕 HEAD，形成两段串行存储等待；旧版授权不做这些 R2 检查。

| 路径 | D1 等待并集中位数：之前→之后 | R2 等待并集中位数：之前→之后 | R2 补测配对数：之前/之后 |
| --- | --- | --- | --- |
| watch-data | 705→400 ms | 0→501 ms | 5/5 |
| media-range | 378→260 ms | 519→503 ms | 4/5 |
| renew | 451→332 ms | 0→508 ms | 4/5 |

这一变化对应 `1c34611` 的签发前媒体版本/大小校验。它是当前安全契约，不应通过删除 R2 校验、跨请求缓存权限或跳过最终配额条件来消除回退。独立 MP4 与字幕 HEAD 的串行调度不是安全所需依赖；共享签发函数的最小修复及其单变量实测见[下节](#并行修复的同条件复测)。首次对照跨越多个业务提交，不能把这些数字归因于身份优化本身。

媒体 Range 的 D1 往返和中位 TTFB下降，但初始新版样本的 P95 仍有约 3 秒以上尖峰。补充 R2 样本较平稳，数量不足以证明尾部问题消失；保留尖峰，不把它们随意删作异常点。总体性能验收保持阻塞。

### 查询、扫描与归因边界

- 首页/剧集/电影并行 loader 的重复工作减少，但原关键链仍近似为基础身份加片库读取，不能把减少的并行调用数直接换算为 TTFB 提升。
- 播放页原生 session SELECT 为 3→1，普通只读页面为 2→1；媒体仍为 1→1。新的 HTTP 请求仍读主库，没有 Cookie 缓存、跨请求身份缓存或只读副本。
- staging 原生 `/api/auth/get-session` 为 8→6，而本地报告为 7→5。本地夹具逐请求切换虚构 IP，云端同一 IP/路径桶的采样跨过 10 秒窗口；锁定库窗口重置后的到期清理与时间线中额外一条限流调用相符。这不是多一次身份解析，不能为对齐本地预算裁掉限流。
- D1 时间使用调用区间并集，不直接叠加并行等待；保留逐调用起止供核对。R2 记录止于 head/get 响应返回，不包含流正文播放时长。没有把区间排序当成完整因果证明。
- `all/run/batch` 可得的 duration、rows_read、rows_written 已保留；`first/raw` 不返回这些元数据，记录的是已知部分而非完整总量。未把缺失视为 0，未根据不完整扫描量新增索引。
- 原生 session SELECT 次数是锁定 adapter 的查询分类，不是完整库 CPU 时间。库/业务整体 CPU、isolate 内存、全部敏感插件端点的独立耗时及真正冷启动不可得；未伪造或用 D1 等待冒充。
