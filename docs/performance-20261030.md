# 预览环境性能证据

日期：2026-10-30。对象是正式站 Worker `stcn-video-site` 上 `dev` 分支的预览（`https://dev.video.startrekchina.org`），运行代码为 `dev` 的 `15aa0d9`；production 未操作。

开发者未另设延迟或首屏阈值：并发容量按 A/B 的“同时 50 路以内播放”判断，首屏、冷启动和尾延迟只记录数值与原因。费用模型按开发者决定本次不计算（2026-10-30），月预算仍未核定。备份峰值按[大库复测条件](plan/operations.md#692-定时备份执行与失败行为)处理：当前预览备份约 0.79 MB，不在本次范围。

## 结论

- **并发容量**：50 个模拟播放器按 1080p 码率（4.45 Mbps）连续播放 10 分钟，合计约 266 Mbps，服务端无错误、无 CPU 或内存超限，媒体请求全部返回 `206`，进度写入 1,878 次只有 3 次版本冲突。测试条件下满足 50 路。客户端侧有 64 次读流中断和 3 次卡顿（共 190 秒），服务端没有对应错误，更像本机代理链路，未能完全归因。
- **冷缓存首屏**（手机模拟、慢速 4G）：访客首页、剧集页、播放页的 LCP 中位数为 3.7–4.2 秒；成员首页为 15.2 秒，原因是首页直接加载原尺寸海报，图片合计 3.2 MB。中文字体每页 0.76–1.21 MB。
- **冷启动**：空闲 30 分钟后的请求测了三轮，服务端 CPU 中位数 93–102 ms、最高约 0.2 秒，耗时最高 0.45–0.61 秒，均无错误；客户端首字节 0.43–1.23 秒，其中成员首页 0.85–1.23 秒，热请求时中位数为 0.49 秒。
- **尾延迟**：客户端慢样本的大部分时间不在 Worker 内；同一窗口服务端最长耗时 520 ms，而客户端最慢样本为 1,469 ms。

## 方法与环境

- 客户端在本机，经本机代理 `127.0.0.1:7891` 访问，接入机房均为 HKG；预览 D1 主库位于 APAC（KIX）。本机经代理到预览的下载带宽实测单路约 268 Mbps、4 路合计约 475 Mbps，足以承载本次 50 路 1080p。
- 预览库建立 50 个虚构成员、每人一个会话，测完删除；未使用真实成员数据。
- 服务端指标取自 Cloudflare 控制台的预览 Worker 指标（按时间窗的调用数、错误、CPU、耗时、内存分位数）。逐次调用日志未开启，请求级 D1/R2 耗时不可得，服务端数字是时间窗内的分布，不能逐请求对应。
- 预览只有 150 秒的测试片段：原画为 3840×2160 VP9 约 12 Mbps，1080p VP9 约 4.45 Mbps，720p/480p H.264 约 2.6/1.3 Mbps。

## 单路播放

真实浏览器以虚构成员播放一集 150 秒的原画（3840×2160），播到第 60 秒时拖到第 100 秒，再播到结尾（10:57–11:00）：

- 整集只有 2 个媒体请求：开始时一个 `bytes=0-` 的长连接，浏览器按需读取；拖动后从新位置再发一个。播放器另每 15 秒上报一次进度。
- 拖动后约 1.1 秒恢复播放，除拖动外没有缓冲等待。
- 服务端 16 次调用，CPU 中位数 5.6 ms、P90 31 ms，内存最高 30.7 MB。

因此每路播放对 Worker 的请求主要是进度写入（约每分钟 4 次），媒体请求只在开始、拖动和断线续传时产生。

## 50 路并发

脚本按单路播放的模式模拟 50 个播放器（11:05–11:16）：每路一个 `bytes=0-` 请求、最多预读 30 秒、每 2–3 分钟随机拖动一次、每 15 秒上报进度，50 个成员各播三个有片源单元之一的 1080p 档。

| 项目 | 结果 |
| --- | --- |
| 媒体请求 | 551 次（起播 83、拖动 468），全部 `206`；首字节中位数 373 ms、P95 642 ms、最高 1,573 ms |
| 起播（缓冲 2 秒） | 83 次，中位数 0.80 秒、P95 1.29 秒、最高 1.9 秒 |
| 拖动后恢复 | 466 次，中位数 0.54 秒、P95 1.04 秒、最高 2.5 秒 |
| 进度写入 | 1,878 次：`200` 1,875、`409` 3；中位数 339 ms、P95 584 ms |
| 客户端异常 | 64 次读流中断（`UND_ERR_SOCKET`，连接被对端关闭）；3 次卡顿共 190 秒，最长 115 秒 |
| 服务端（10:49–11:19 窗口，约 2,460 次调用） | 错误 0；超内存、超 CPU、内部错误、过载丢弃、未捕获异常均为 0；CPU 中位数 12.9 ms、P99 37 ms、P999 46 ms；内存最高 29.7 MB；客户端取消 74、响应流断开 0 |

脚本与浏览器有一处不同：流读完或中断后，浏览器从缓冲末尾续传，脚本却按原类型从本段起点重新请求。因此起播与拖动请求（50 路只应有 50 次起播）和下载量都多于真实播放，负载偏重，不影响容量结论。读流错误在 3 路、1 分钟的试跑中也出现过 1 次，与并发数无明显关系；服务端没有对应错误，更可能是本机代理断开长连接，但不能完全排除边缘节点断流。长时播放的断流需要在真实网络中观察。

## 冷启动与热请求

每轮先让预览空闲至少 30 分钟，再对五条路径各发 1 个请求（每个请求新建连接），之后读取只含这 5 次调用的服务端窗口。

| 轮次 | 访客首页 | 成员首页 | 播放页 HTML | 播放页数据 | 64 KiB 媒体 | 服务端 CPU | 服务端耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | --- | --- |
| 第 1 轮 12:01 | 577 ms | 854 ms | 906 ms | 430 ms | 1,107 ms | 中位数 102 ms、最高 206 ms | 中位数 424 ms、最高 452 ms |
| 第 2 轮 12:36 | 578 ms | 1,191 ms | 1,000 ms | 427 ms | 672 ms | 中位数 93 ms、最高 207 ms | 中位数 303 ms、最高 611 ms |
| 第 3 轮 13:10 | 574 ms | 1,229 ms | 923 ms | 676 ms | 735 ms | 中位数 98 ms、最高 201 ms | 中位数 310 ms、最高 555 ms |

表中为客户端首字节；TLS 建连各约 110–180 ms。三轮均无错误，内存约 31 MB。冷请求的服务端 CPU 约为热请求的两倍；成员首页扣除 TLS 后为 1,048–1,082 ms（第 2、3 轮），比同轮服务端最长耗时多出约 0.5 秒，而热请求的中位数只多出约 35 ms。多出的部分不在服务端计时内，可能是新实例启动或连接建立，现有数据无法再区分。

## 尾延迟归因

- 热请求中最慢的是成员首页的第一个样本：首字节 1,469 ms、扣除 TLS 后 1,337 ms，而同一窗口服务端最长耗时 520 ms，至少约 0.8 秒不在 Worker 计时内。可能来自代理与网络排队，也可能是请求落到新实例的启动时间（平台不计入服务端耗时），现有数据无法再区分。
- 10-22 复验的慢样本主要耗在 TLS 建连；这次 TLS 中位数约 120 ms、最高 391 ms，那批慢样本更可能来自当时的本机网络。
- 服务端耗时中位数约 0.3 秒，其中包含 HKG 的 Worker 访问 KIX 的 D1 主库的往返；没有请求级探针，不能再细分。
- 成员的真实网络与接入机房只能在上线后用路由日志的 `colo` 字段观察（[T4.5.8](plan/authentication.md#t458-数据位置与成员机房测量)）。
